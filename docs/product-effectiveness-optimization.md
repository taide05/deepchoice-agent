## 当前内容验收边界

旧八小时计划及其三类请求加一次重复的四报告批次已经结束，0/4 结果和全部
原始材料保持历史原状。下一轮**舍弃所有 Codex 时期使用过的例子/题**：
不把旧问题、改写题、同技术组合与约束的变体用作开发预设、内容验收、
保留集或成功分母。旧材料只为解释历史失败和核对机制，不作为新题调参输入。
下一轮题目由独立准备者产生并与旧题查重；实现者冻结候选后才接触未见题。
开发修复阶段每个修复包完成后先用一份全新题报告检查效果。题目、必答项、来源政策、候选身份、
额度和停止线应在单例运行前冻结，且不得根据输出换题或改 rubric。未获新额度时只可
离线准备协议及获委托的材料。语义内容判定沿用第 2 节；单例通过是进入小规模校准的
阶段门槛。最终交付需要代表性样本、可信指标和基线比较，不能自动恢复旧四例、八场景或最终 24。

## 1. 新题集与运行身份

连续单例题应逐步覆盖不同技术取舍、硬约束、需求缺项、来源版本与适用范围。
独立准备者先查重 Codex 期间所有已用题及近义改写，保存查重结论，
再冻结原始请求、影响选择的必答项、可接受的条件判断、严重性锚点、
数据集 ID/hash、来源政策与暴露状态。任何用于开发反馈的题立即失去未见资格。
同条件比较须冻结基线与候选 commit、资产/manifest、模型参数、依赖、
检索/缓存策略、HITL、采集器、环境与各自额度；失败照计。
下一轮题数和研究成本由新授权决定，旧数据集不能自动成为基线或验收集。

### 1.1 代表性与数据隔离

- 规划百例以上的独立需求；精确样本数由支持范围、类别覆盖、期望测量精度和预算共同确定。
  不用同一题的措辞改写堆数量；同主题/同技术组合的相关需求按组划分，避免跨集合泄漏。
- 在看输出前定义领域、任务类型、难度及类别权重。覆盖候选对比与开放选型、不同硬约束、
  来源冲突/不足、版本条件和需要澄清的需求；报告每类数量。自建分层集须说明抽样方法，
  不能把人为类别占比当成真实用户分布。代表性首先相对于声明的支持范围成立。
- 分开开发材料、小规模校准集与最终未见评测集。用于修复或评审校准的题不进入最终分母；
  不预先用未见题或参考答案制作提示示例、知识库、学习文档或检索缓存种子。正式运行只输入
  协议允许的原请求及澄清，参考答案不投喂系统。既有已见题仍只作历史诊断。
- 每例冻结原请求、约束、必答项、允许的条件性结论、参考依据及日期/版本、可答性、暴露状态。
  参考依据供评审使用，不投喂系统；不强求唯一推荐，不以命中产品名代替回答正确。
- 独立准备与查重后冻结数据集 ID、版本、hash、日期、分组与切分清单。候选锁定前实施者
  只接触类别及协议；正式执行期间不据反馈改代码、提示、参考答案或评分规则。
  如需修改，关闭当前版本并保留结果，已暴露题转开发材料；后续正式结论使用新的未见集。

## 2. 报告内容判定

每例只评原始选型需求；普通问题不能因提到迁移而被扩展成完整部署/回退验收。每份报告记录下列检查、理由和不可评项；五项均通过且无关键错误才记为“可用且有据”。结构字段、引用计数、自评分和正文长度均不能替代正文判断。

| 检查 | 通过条件 |
|---|---|
| 约束与回答 | 不违背硬约束；回答影响选择的必答项，或具体说明缺口及其决策影响 |
| 有用建议 | 有理由的选择或条件分支、关键取舍与可观察的改变条件；不能只给通用清单 |
| 决定性依据 | 改变选择、排除候选或界定风险的事实有保存的适用来源；推论列出前提且不过界 |
| 不确定性 | 明确未知与场景假设；说明能答与不能答之处，既不夸大也不无差别弃权 |
| 一致与安全 | 摘要、分析、结论一致；不捏造能力、实测阈值或来源，不保证危险操作安全 |

**关键错误**包括违反硬约束，捏造决定性能力、来源或测量，反转关键因果/适用条件，缺依据却关键排除或保证，以及可能丢失数据或破坏安全的操作。即使建议碰巧合理也记录。**重要缺口**使用户无法理解当前选择或下一验证点，对应项不通过；**一般问题**如格式、重复和非决定性旁支引用不单独否决报告。不能因字词出现就机械定错，须说明是否影响本案选择。

对每条决定性判断，保存报告定位、原引用、来源保存位置及版本、适用前提、支持/部分支持/不支持/未知和严重性。事实、来源支持与推论分别核查；新查资料不能回填原报告的引用。记录原问题实际回答、检索与合成的来源事实、绑定/核验/渲染前后信息损失，及 token、调用、耗时。来源不可达或跨语言不确定保持 `unknown`，不能据此认定主张虚假。

### 2.1 决定性断言的采集范围

评审先按冻结的字段清单对**整份已服务报告**做普查，再判断支持；不得只看带引用编号的句子，
也不得用关键词或抽样替代。采集范围：

- **纳入**：任何改变主推荐/条件分支、候选保留或排除、风险或安全边界、验收/反转条件的事实
  陈述、否定陈述（如“X 缺少 Y”）、量化断言、对来源/版本适用范围的断言，以及条件性结论
  所依赖的前提。包括未引用或引用无法解析的断言；它们按“无支持/未知”记录，不因未引用而跳过。
- **不纳入**：纯标签/字段名、导航链接、流程说明、一般背景与定义、格式性重复；重复出现的同一
  判断只计一条并在备注记录重复位置。若一句包含多个可独立判断的断言，拆成多条；不可分割的
  复合句保留为一条并写明范围。
- **采集边界**：审阅前冻结报告字段/定位清单（建议覆盖 recommendation、winner_rationale、
  confidence_rationale、ranked_options 全部字段、trade_offs、evidence_summary、scene_fit_note、
  conflicts 的 resolution/reasoning/key_factor、unresolved_questions 及各格式渲染的正文）；
  不因报告长度临时换抽样。若无法完成全量采集，该例记 `E` 未完成而非通过，并保留未采集范围。
- 每条记录报告原文定位、原文、来源身份/保存位置、来源日期或版本、适用前提、支持状态
  （full/partial/none/unknown）、严重性及是否为推论；推论单独核查前提和适用范围。
  决定性事实的**分母**是完成采集后确认纳入的条数，不是关键词命中数，也不是引用条目数。

## 3. 开发判断与独立复核

局部回放只证明该局部行为。开发修复阶段每包一份原始报告可判断该题是否可用及本轮暴露的问题；
跨问题收益仍须由后续预冻结的新题集、原始报告和保存来源证明，且不能引入新的关键错误
或已有通过能力的实质退化。
连续两种实质方案无收益时停止该机制并重新定位。
评审先看请求、原始报告和来源，锁定内容判断，再看 Trace 与成本；
可盲评时盲评，否则标明。独立复核争议与通过结论，未解分歧不算通过。
助手评审不冒充用户或领域专家，不向默认链路加入 LLM 裁判。

小规模校准须在正式采集前固定评审操作：评审单位、严重性锚点、引用支持判定、盲评方式、
复核比例及分歧处理。正式集的全部报告按第 2 节评审，通过项、关键错误和不确定项按冻结
规则独立复核；记录评审者类型、实际复核覆盖与一致性。若只有助手评审，必须明示该限制，
不能声称已人工校准。未评审或未解分歧不计通过，保留单独状态；没有证据不能推成零错误。
评测侧模型裁判如以后获授权，须另计费用并经独立标注校准，不能直接以模型打分作为真值。

## 4. 正式评测指标、基线与交付

旧八场景与最终 24 次方案不作为当前评测协议，最终 24 仍封存。数据设计与工具核对可在
单例验证期间离线进行；真实校准和正式采集须分别满足路线阶段条件与明确授权。

### 4.1 指标与分母

所有指标附数据集/切分、版本、测量日期、代码/模型身份和 n/N。主表按每个独立 case 的首次
研究运行计算，节点内重试计入该次用量，重复性实验另表记录。设 N 为冻结计划例数、
S 为已派发例数、R 为取得原始报告例数、E 为完成语义评审例数；分别报告 N、S、R、E，
未执行例附原因。分母为零时记为不适用，不填零通过率或零错误率。正式集未完成时只发布阶段结果，
不能把成功子集当作整套验收。

| 指标 | 定义与限制 |
|---|---|
| 端到端有据回答可用率（主指标） | 满足第 2 节全部条件且无关键错误的原始报告数 / S。运行失败、未得报告、未审定均不计通过；另列 E/R 评审覆盖率 |
| 必答项有据覆盖率 | 每例获得适用来源支持的已回答必答项 / 冻结必答项数，再按预定类别权重汇总；明确未知的项不算已回答，不用字词命中计分 |
| 关键错误率 | 含至少一项关键错误的报告数 / E，同时列 E/R；无报告及未审定不是“零错误”，另报 / S 的已发现错误占比也不能冒称完整错误率 |
| 决定性论断支持率 | 充分得到适用来源支持的决定性事实论断 / 全部被审查的决定性事实论断；包括未引用论断，部分支持/不支持/未知分列。推论单独检查前提与适用范围，报告每例及汇总口径 |
| 运行完成与产物一致性 | 可查询完整结果的任务数 / S；保存/快照/展示/导出检查通过数及其检查分母另列。取得结果不等于内容通过 |
| 不确定性处理 | 按预先标注的可答/证据不足类别，报告恰当保留未知、无依据断言及过度弃答的数量/分母。诚实缺口不自动算满足必答项，也不自动判假 |
| 效率与资源 | 报告完成任务的研究墙钟 P50/P95 和样本数；另列所有任务的终态耗时、失败/超时，预加载及排队单列。报告实际 LLM/检索请求（含重试）、token、费用与预算拒绝；缺失用量或价格保留 unknown |
| 基线增益 | 同一未见题集上候选与简单基线的主指标、关键错误、延迟及资源差异；同时给出各自绝对值、分母和不确定性，不只给提升百分比 |

Top1 仅对预先可判定的推荐集合提供辅助指标，允许条件性答案；不得代替主指标。
现有 `report_quality.py` 的 A/B/C/D 是五项结构检查，来源绑定率也不等于论断支持率。
这些现有工具尚不能直接实现本节全部语义指标；需先核对采集/评审能力再正式测量。

### 4.1.1 case、run、请求、重复测量与墙钟的计数

- **case**：一个独立需求组，按第 1.1 节冻结。N/S/R/E 的正式定义与分母口径见 4.1，不在此
  重复；这里只补计数边界：S 的“派发”按一个 case 的**首次研究运行**计，后续重复/恢复不增加
  S；R 按首个运行取得原始报告计；E 按完成语义评审计。基线臂若单独执行，也按每 case 首次
  运行计入同口径 S/R/E；候选与基线分别报告自己的 S/R/E，S 共用 case 集合，不把两臂 run
  数相加作为 case 分母。共享采集不增加 case 数，分臂调用单列。
- **run**：一次有独立身份、预算和终态的完整研究执行；节点内重试、LLM 重试和工具重试属于同一
  run。**同一 run 的兼容恢复（interrupted resume）仍是同一 run**；关闭旧 run 后的新执行
  或在不可恢复终态后重新派发才另计 run。所有 run 全量保留，主表只用每个 case 的**首次 run**，
  额外 run 另表列出，不把成功后补跑改写成首轮通过。
- **请求**：实际发出的 LLM 请求与检索 HTTP 请求，按类型、按候选/基线/共享采集分列；含重试、
  探测和健康检查的请求单独标记，不与研究请求相加成一个“有效请求数”。预算预留不等于实际
  请求；供应商成功响应与实际消耗分开记录；preload、排队不计研究请求，但计入资源/墙钟说明。
- **重复测量**：按预冻结子集与重复次数执行；每次重复是一次 run，消耗额度，但不增加 case 分母。
  报告首轮主指标、重复轮波动/失败和全部结果，不取最优一次；唯一 case 数与研究运行次数在
  所有表中分列。
- **墙钟**：研究墙钟定义为该 run 的研究执行 `started_at` 到终态的时长，含节点内等待与重试；
  接受/排队前等待、服务预加载和 review 时间不计入该口径，分别单列。若 run 发生
  `interrupted`/`waiting_for_input` 暂停，暂停时长必须单列并从研究墙钟扣除；若冻结口径选择
  计入，须在 manifest 明示，不能把包含多日暂停的墙钟当作 900 s 停止线内的研究耗时。
  端到端 case 墙钟如另计，须单列预加载/排队；评审与标注工时、数据准备工时不进入研究效率
  分母。停止线使用冻结的研究墙钟口径。

### 4.2 公平比较与测量精度

- 预先冻结一个可解释的简单基线，例如同模型的检索后直接综合。明确基线的实际实现、
  输入与检索能力，不能将无检索基线的劣势全部归因于复杂工作流。可另做固定证据对照，
  但其结论只覆盖推理/综合，不与实时端到端评测混算。
- 配对比较使用相同问题、参考标准、模型版本与参数、供应商/来源政策、缓存及知识库政策、
  澄清/HITL 输入和可用预算上限；保留两边实际消耗。冻结运行顺序与时间窗口，控制来源更新
  和缓存预热影响；无法控制的差异明示，不把不同时期的历史运行冒称同期因果对照。
- 同时报告类别结果与预定权重的汇总结果。区间估计方法在运行前确定，相关变体按需求组
  处理；配对差异按 case/需求组计算不确定性，不能把一份报告的多个引用当作独立样本扩大 n。
  小类别样本不足须标明，不依据几个百分点的点估计直接宣布胜出。
- 重复性采用事先选定的子集与重复次数，每次调用都纳入预算；所有结果保留，报告波动，
  不择优取一次。唯一 case 数与研究运行次数分开，重复运行不增加独立 case 分母。

### 4.2.1 共享证据基线的输入截取点与成本归属

- **截取点**：共享证据快照固定在“检索完成 + 来源评分之后，冲突检测/证据链生成/综合之前”。
  实际顺序是 source evaluation → conflict detection → evidence chain → synthesis；因此快照
  只含每个来源的 URL、标题、已保存正文、`has_body`、日期/版本（如来源记录提供）、provenance、
  检索评测分 `total_score` 和来源失败/空状态，不含冲突裁决或证据链派生的 disputed 标记。
  按内容 hash 冻结，候选和基线读取同一快照。
- **基线输入**：综合输入由冻结的 case 请求/场景字段 + 该快照的确定性序列化组成（相同字段
  顺序、同一有界截断函数和同一每例 token/字符上限）；基线不读取候选的冲突裁决、自审、修订
  或额外工具内容，manifest 记录序列化函数、截断长度/条数和被排除来源。候选的冲突/证据链/
  自审/验证属于候选增量，不回填共享快照；禁止候选按题增加或改写来源而不给基线同样的快照
  与上限。两侧使用同一模型/参数、引用绑定和报告渲染路径。
- **共同能力**：检索、来源身份、可用正文、失败/空状态、来源政策属于共享能力；冲突检测、
  自审循环、额外验证、重试编排属于候选增量。基线不因缺少候选增量而被扣分，候选也不因
  拥有增量而自动获得证据优势——两者必须在同一快照上分别报告。
- **成本归属**：配对比较时共享检索只执行一次，其请求/token/费用记入“shared acquisition”
  bucket，不重复计入两臂；候选增量调用与基线单次综合调用分别记入各自臂。总资源表同时列
  shared + candidate-arm、shared + baseline-arm，并单列各自墙钟；若因基础设施必须分开执行
  检索，则每次实际请求计入执行它的那一臂并在方法中说明，不能把同一调用同时算给两臂。
  共享检索失败对两臂同样记失败，禁止只给其中一臂重试或补搜；每例的共享与分臂配额均须在
  冻结时明确，未知用量/价格保留 `unknown`。

### 4.3 冻结与结论边界

正式采集前须具备：支持范围、样本/切分与去重记录、可复核参考标准、评分/独立复核规则、
基线和候选身份、每项指标计算方法、类别权重与区间方法、内容/关键错误/资源达标阈值、
重复性计划、实际运行器和授权总额度及停止线。目前不填未经同意的具体阈值、样本数或金额。
执行中保留所有原始结果；内容失败按冻结矩阵继续或结束，不能临时改规则筛掉低分。
仅完整执行且达到冻结标准才可称达标；未达标也交付真实测量结果及限制。
发布指标附最小脱敏证据与复算说明，旧 300-case、smoke-v1、开发单例及新正式集各自独立。

## 5. 运行、异常与记录

只在有实质候选或需排除关键假设时做付费开发测量；开发、校准、基线、正式采集及评审外呼均须被当前明确的总额度覆盖。授权应说明阶段、case 数、运行次数、重试/探测、每例与整批上限、身份及停止线，范围内不逐例请示。现代产品测量走 durable API 与隔离输出目录，不直接写生命周期表；恢复实验按单独冻结的旧接口记录，不能混为现代产品验收。正式采集先选定交付分支与实际运行器。每个 run 保持自身冻结预算政策；新增额度和准入精确登记，未知花费不写零。准备探测和研究成本分开。失败格不退款、不择优补跑。

### 6.1 支持范围与数据设计

**声明支持范围**：有明确候选对象和可执行硬约束的技术选型/对比需求，决定性依据可从公开来源
获得，且允许条件性推荐。暂不声明覆盖：无候选的开放研究、采购/法务/许可最终判断、需要生产容量
实测才能回答的问题、需要直接执行变更或凭据验证的操作、以及只能依赖实时价格/漏洞/版本且无法
记录日期的判断。落在支持范围之外不等于报告失败，但不得进入正式分母。

**分层与候选配额（规划 N=120 个独立需求组，供冻结讨论）**：

| 类别 | 主要检验点 | 规划配额 | 说明 |
|---|---|---|---|
| A 核心候选对比 | 主推荐、关键取舍、双方依据 | 30 | 含至少两个真实候选，不能只列优缺点 |
| B 硬约束与失败模式 | 约束遵守、排除/保留证据、风险边界 | 24 | 如网络、数据、预算、运维隔离 |
| C 证据不足/来源冲突 | 诚实未知、条件性结论、冲突处置 | 18 | 必须允许“无法确定”而非强行选一个 |
| D 版本与适用范围 | 版本条件、EOL、适用范围、来源日期 | 16 | 选择依赖版本/配置差异 |
| E 需求含缺项/需澄清 | 不越界、明确缺口及决策影响 | 16 | 不要求系统必须向用户提问 |
| F 安全/成本/长期维护 | 安全降级、长期成本、可逆性 | 16 | 不要求给出未经测量的数字 |

配额按“独立需求组”计，不按措辞变体计；同一技术组合或同一决策的改写题只保留一个主 case，
其余变体归入同一 group 且不重复计入 N。类别权重建议在冻结时按支持范围重要性确定（例如
A/B 高、C/D 中、E/F 中），同时报告未加权类别结果和加权汇总；权重不得在看到输出后调整。

**隔离与冻结**：
- Codex 时期使用过的题、案例、技术组合及近义改写只作历史诊断，不得进入开发预设、校准集或
  正式未见集；独立准备者先做查重并保存结论。
- 开发材料（历史失败诊断和机制回放）、小规模校准集、正式未见集三套清单分离；用于修复反馈
  或评审校准的题立即失去未见资格，不进入最终分母。
- 每例冻结：数据集 ID/版本/hash/日期、原始请求、约束、必答项、允许的条件性结论、参考依据
  （URL/日期/版本/适用前提）、可答性、类别/难度、需求组、切分与暴露状态。参考答案只给评审，
  不投喂系统、不进入提示、知识库、检索缓存或学习材料。冻结的是**评审规则、必答项和严重性
  锚点**；实际决定性断言不预列封闭清单，须在运行后从完整报告逐条采集，包含未预见、未引用
  的断言及其适用条件。
- 正式采集前冻结支持范围、manifest、去重/分组记录、评分与复核规则、基线和候选身份、类别
  权重、不确定区间方法、内容/关键错误/资源阈值、重复性计划、运行器和总额度。实现者在候选
  锁定前不接触未见题；正式执行中不因反馈改代码、提示、参考答案或评分规则。
- **封存交接（简单流程）**：准备者完成 proposal/payload/run record 后明确停止写入；执行者用
  `D:\\deepchoice-precodex\\scripts\\seal_case.py`（或同等的只读复制）把完整文件复制到**新的
  独立目录**，写入 file/canonical/payload/query hash 与冻结评估环境，拒绝覆盖已有 seal；
  执行者核对 `verify_seal` 后才能派发。运行后的报告、快照、addendum 与复核记录写在 seal 外，
  **绝不修改 seal 内文件**。每次真实/校准运行显式冻结 `LEARNED_DOCS_READONLY=1` 与
  `RETRIEVAL_CACHE_ENABLED=0`，并记录 learned-docs/cache 的实际 hash/状态；没有这些记录时
  不能把运行当作可复用身份。

### 6.2 评审设计

**评审单位**：每个 case 的首次研究运行及其原始报告；节点内重试计入该次用量，重复性实验单独
计入 run 表，不增加独立 case 分母。评审先看原请求、报告和保存来源，锁定内容判断后再看 Trace、
token 和成本；不得先看成本替内容找理由。

**记录结构（最小 schema，正式运行器可据此落库/导出）**：

| 字段 | 内容 |
|---|---|
| case/run 身份 | 数据集版本、case_id、需求组、run_id、报告/快照/展示/导出 hash、采集时间 |
| 必答项 | 每项状态 `answered_supported` / `answered_unsupported` / `partial` / `unknown_meaningful` / `missing`，绑定报告定位与来源；`unknown_meaningful` 不算已回答 |
| 决定性事实 | 每条改变选择/排除候选/界定风险的事实：报告定位、原句、来源身份与保存位置、来源日期/版本、适用前提、支持状态（full/partial/none/unknown）、严重性 |
| 关键错误 | 类型、定位、证据、严重性；类型至少含：违反硬约束、捏造决定性能力/来源/测量、反转关键因果/适用条件、无依据的关键排除/保证、不安全操作 |
| 不确定性 | 明确记录未知/可答边界、无依据断言、过度弃答；诚实缺口不自动算满足必答项，也不自动算错 |
| 来源适用条件 | 来源是否被用于其实际覆盖的版本/场景/候选；发现标题替代正文、单来源外推或集成文档扩大为产品语义时记录 |
| 一致与安全 | 摘要/分析/结论一致性、来源身份贯穿、脱敏/安全检查、格式/渲染损失 |
| 结论 | `usable` / `not_usable` / `needs_review`，附理由和关联 error id；未评审或未解分歧不记通过 |

**冻结评审规则**：
- 评审规则、必答项、允许的条件性结论和严重性锚点在运行前冻结；**决定性断言不预列封闭清单**，
  运行后从完整报告逐条采集（含未预见、未引用断言），采集范围按 2.1。运行后不得按报告内容
  增删必答项或改严重性；不得用预列清单漏掉清单外断言。语义判定沿用第 2 节五项；结构字段、
  引用数量、自评分、关键词命中不能替代。
- 关键错误按“是否影响本案选择/风险理解”判定，不能因字词出现机械定错；重要缺口使读者无法
  理解选择或下一验证点时对应必答项不通过。一般格式/重复问题不单独否决报告。
- 来源支持须对照保存正文与版本/日期；来源不可达或跨语言不确定保持 `unknown`，不能据此判假。
  新查资料不能回填原报告引用；只能记录为对后续验证有价值的补充。
- 允许条件性答案；Top-1 仅作辅助指标，不以命中产品名称代替回答质量。

**独立复核与分歧**：
- 开发单例和校准阶段由未参与实现者按冻结规则评审；正式阶段至少完成全部 case 的第一评审，
  并建议对失败/含关键错误/低置信 case 100% 第二评审、对通过 case 做分层随机第二评审（比例
  在冻结时确定，候选 25%–35%，不得声称人工校准）。报告评审者类型（人工/助手）、实际复核
  覆盖、盲评方式与一致性统计（两个以上评审者时可用 kappa；样本不足时只报原始一致/分歧）。
- 盲评优先；无法盲评时明示。分歧按证据定位逐条裁决，未解分歧标记 `needs_review`，不计通过。
  助手评审只算助手评审，不冒充人工或领域专家。默认链路不加入 LLM 裁判；如以后授权模型评审，
  须另计费用、与独立标注做校准，且不能直接当语义真值。
- 任何用本仓库 `report_quality.py` 结构清单、关键词、引用绑定率或测试通过数推导“可交付/质量
  合格”的做法都无效；历史 300-case 数值与 smoke-v1 结果不得与新分母合并。

### 6.3 简单基线

建议冻结一个可解释、可复现的简单基线：**同一检索包 + 单次综合**。即对同一 case 使用相同候选、
原请求、场景、六源检索结果（含失败/空来源状态）、来源政策、模型/版本/参数、缓存关闭和相同的
来源上限，直接复用 `conclusion_synthesizer` 的提示/JSON 契约做一次综合与确定性引用绑定，不运行
冲突扫描、自审、重试或多节点编排；报告仍走同一渲染/引用路径。共享证据的截取点、基线输入
序列化与成本归属按 4.2.1 执行。另可增加“固定证据包 + 单次综合”的推理对照，只说明综合能力，
不与实时检索端到端结果混算。

公平性要求：同一题、同一参考标准、同一模型版本/温度、同一检索结果与来源上限、同一 HITL/
澄清策略、同一时间窗口和缓存政策；候选与基线各自保留实际调用/token/耗时，失败照计。为避免
把无检索的劣势归给候选，禁止使用“无检索基线”作为唯一对照；若基线检索失败，按同一失败记账。
基线获得与候选相同的每例总 token/调用上限（上限相同，实际消耗分别报告）；运行顺序冻结/分块，
防止来源更新与缓存预热不对称。基线也需通过同一语义评审规则，不使用结构化清单代替。

**已实现的离线配对入口（2026-10-21，实验树）**：`src/deepchoice/evaluation/simple_baseline.py`
与 `scripts/run_pair.py` 从同一“检索完成 + 来源评分之后”的状态冻结共享证据；基线只跑确定性
证据序列化→一次综合→现有引用绑定/渲染，候选臂保留冲突/证据链/综合/自审。两臂共享原请求、
来源正文、证据预算和来源身份，增量 LLM token/调用、质量信号与共享检索请求分开记录；入口默认
离线，未注入模型或未显式 `--allow-external` 时拒绝外呼。该实现不替代正式运行器，也不改变
基线/候选各自的 S/R/E 与评审规则。

**下一轮比较的数据与预算（尚未授权）**：数据按预先声明的支持范围和难度分层选取，不能按
抓取成功/失败挑题；保留复杂场景、来源失败与 unknown，不用本机保存的第八至十次题作正式
分母。比较仍以百例以上、公平基线、质量/可靠性/效率、完整使用链路为最终目标；单次开发对照
不是正式通过率。建议作为下一次具体授权的上限（需用户冻结后才生效）：1 个固定 case ×
2 arms（共享采集一次；Tavily ≤24、official ≤4 page attempts/≤12 HTTP、每页 15 s/≤200,000
bytes）；LLM 总 ≤48（基线单次综合 + 候选增量，含 fallback/重试）；总墙钟 ≤1800 s（两臂各
≤900 s，预加载/停止清理单列）；外部模型裁判/付费基准 0，费用 unknown。任何一臂失败按失败
保留，不补跑、不择优换题。

**第十一次真实配对的实际结果（2026-10-22，开发诊断）**：一次共享采集后 baseline→candidate，
模型/参数、来源正文和证据预算相同，baseline 只综合一次，candidate 走既有冲突/证据链/综合/自审；
接入和预算均未越线（LLM 5/48、Tavily 7/24、official 4 次页面尝试/7 次 HTTP、总墙钟 232.735 s/1800 s），
但独立盲评显示两臂都未通过内容证据门：决定性 claim 依赖 snippet-only/第三方材料，OpenTelemetry
官方正文因 `content_too_large` 未取得；candidate 为 `not_usable`，baseline 为 `needs_review/
not accepted`（不是可用通过）。因此按预定 R4 保留失败、停止自动研究与修复，不选下一阶段路线，
也不启动校准/百例评测或第 12 次。N=1 只说明该次配对诊断失败，不形成正式通过率或统计性结论；
若继续，须先由用户另行授权解决来源获取或准备新题/新 seal，不能在失败运行上补跑/手修报告。
基线成本更低（1 call/17,769 tok/46.2 s）而 candidate 为 3 calls/47,175 tok/134.8 s，只是成本
事实，不构成内容胜出；费用仍 unknown。该实测不改写前述输入截取点、基线定义或共享证据规则。

**第5轮页面证据澄清（2026-10-22，仅用于未来协议）**：来源权威性、可用原文摘录、搜索摘要、
必要上下文和版本/日期适用性必须分开记录。一个页面被成功抓取、目录存在或有一小段介绍，都不
等于它具备决定性证据；导航/目录页只能作为线索。只有实际取得的原文段落（含必要标题上下文）
可以在其明确版本/范围内支持论断；搜索摘要或无法取得正文的链接不能支持决定性结论，必须保持
unknown。页面级采集验证只证明采集表现，不是报告通过率、未见评测或路线胜出；下一轮正式运行
前必须把页面探测使用的诊断 cap 与正式运行 cap 对齐，并显式说明未抽取的列表项等结构限制。
本轮不改变第11次的内容标准或结论。

**第12次开发配对结果（2026-10-22，N=1）**：独立准备 Temporal vs Camunda 新题，封存后执行

**这一定性只是诊断性评价，不是冻结门槛通过**。两臂均推荐 Camunda，但 5 个必答项均只 partial、
0 项达到 rubric score 3，版本化官方 human-task/audit 证据也不足；**正式验收统一为两臂均未
通过**。按冻结规则停止自动研究路线，不安排第13次、同类补丁、校准或百例评测。N=1 不构成
统计性优势或正式通过率。来源统计须区分“取得正文”和“权威且适用的决定性证据”：3 个 unique
full-body 页面分别是产品营销页、社区帖子和 SDK 文档，不是三份合格官方依据；仍有 23 个
snippet-only 行和 1 个 403，不能由同路径补丁修复。决策契约另有缺口：当前综合输出主要要求
产品 winner 或平局，空 winner/constraint-fit 校验/默认渲染可能补选产品，自审不能撤回 winner；
这是当前代码机制，**不是**已证实的第12次历史因果（原始模型输出未保存，不能断言曾产生 hold
又被覆盖）。若未来继续，须用户另行授权新的证据获取/新题与预算，不得把 lower-band 或
needs_review 升级为正式通过。

**第7轮决策契约（2026-10-23，离线）**：正式决策使用 `decision_status`：`recommended` /
`conditional` / `insufficient_evidence`，解析、结构或执行失败为 `invalid`。只有
`recommended` 允许有 winner；条件选择和证据不足暂缓不得被 ranked options、constraint-fit
或任何 renderer 补选；invalid 不得伪装成有效暂缓，低 confidence 不等于证据不足。自审可整体
撤回无依据推荐并转为暂缓，但不能换成另一个赢家、自动升级或把 invalid 转成 hold；失败/无效
自审不应用撤回。三种报告格式、保存状态和引用消费者必须使用同一决策口径；缺字段的历史记录
只展示已保存 winner，不得从 ranked options 推导。该契约只证明决策能被正确表达和保存，不是
模型判断正确、内容验收、校准或正式指标。

### 6.4 工具缺口与正式运行器最小能力

现有可复用能力（离线核对）：`benchmarks/run_baseline.py` 能按 JSON case 调研究管线、保存
报告/状态/用量并汇总；`benchmarks/metrics.py` 能算 Top-1、来源召回、词法 claim grounding、
冲突检测（当前实现依赖 LLM judge）和延迟/成功/token；`benchmarks/report_quality.py` 只有五项
结构/关键词检查；实验分支现有测试覆盖保存报告/快照/端点/导出一致性、引用身份与未知语义。
这些不能实现本协议的语义指标，也不等于内容质量。

实验分支候选 `f07f87b` 已把 `report_quality.py` 的活动输出改称“结构清单”，并保留历史键/数值；
它不改变本协议要求。该候选同时修复了多查询覆盖、元数据非正文、冲突主张取正文、综合/自审
输入完整性及展示定界等离线机制，但这些只是候选机制修复，真实内容收益仍须由另行授权的新题
原始报告验证，不能据此声称任何语义指标已达标。

正式运行器最小缺口：
1. 数据集 manifest 加载/校验：版本、hash、日期、分组、切分、暴露状态、支持范围；拒绝重复
   case 进正式分母，拒绝开发/校准题泄漏到未见集。
2. 候选与基线两种运行模式：同一检索包与统一每例上限，保存两边原始报告、来源、snapshot、
   annotated/export hash、用量、失败原因；支持配对 case 与重复子集。
3. 评审记录 schema 的导入/校验/聚合：必答项、决定性事实、关键错误、未知、来源适用条件、
   复核者/盲评/分歧；计算 N/S/R/E 分母和按类别/权重汇总，拒绝零分母通过率。
4. 人工/助手评审的盲分配与覆盖统计、校准集双评一致性；不在默认链路加入模型裁判。
5. 与运行器分离的产物一致性检查和成本/未知项记录（费用未知写 unknown，不写 0）。
6. 冻结规则的版本化与重放（只读）；不建通用评测平台，不提前生成/阅读正式未见题。
