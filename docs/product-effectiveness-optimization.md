用户最新执行约束（2026-09-16）优先于下文原批次计划：不跑 12-case 付费并发，也不跑整组串行。O1-R 单例样本观察不自动恢复批次；先离线诊断，再逐次决定单例，不自动排队。原 48-run 额度不是恢复批次许可，剩余 5 不自动使用；恢复须重新确认，见 [O1-R](o1r-single-case-reliability.md)。

## 1. 目标与策略

当前缺口是缺少默认 durable 路径的真实报告基线。首轮目标：用小样本定位最影响技术决策的
1～2 类问题，证明一次针对性改动是否改善正确性、证据支持或执行成本。

先完成模型适配，再冻结案例和评价规则、测新基线，随后改一个主要变量并复测。保留现有工程能力；复用现有
Python、任务 API、SQLite、版本资产和观测数据。企业级基础设施扩展、演示筛选和面试材料
不属于本轮。历史经验约 6 分钟/20,000 token 仅供背景参考，不作为当前基线或验收门槛。

## 2. 案例：12 例，串行与并发成对测量

数据集拟命名 `product-baseline-v1`，与 12-case 离线 smoke、2026-08-31 的历史 300-case
benchmark、后续 Qwen adaptation 集分别记录。以下是选题槽位；技术名只是候选，不预设胜者。

| ID | 拟选场景 | 必须检验的问题 |
|---|---|---|
| P01 | 个人低写入量应用：SQLite / PostgreSQL | 简单需求下是否避免过度设计 |
| P02 | 小团队知识库：关系库向量扩展 / 专用向量库 | 运维资源、数据规模与检索能力的取舍 |
| P03 | Python API：FastAPI / Django | 既有系统、后台功能和团队经验是否影响结论 |
| P04 | 长任务执行：进程内任务 / 持久任务队列 | 重启恢复、交付保证与实现成本的条件边界 |
| P05 | 中文技术选型问题，关键依据主要是英文官方资料 | 跨语言引用是否实际支持中文声明 |
| P06 | 供应方运行时微基准与业务负载条件不同 | 是否解释外推边界，不预设已有相反实测 |
| P07 | 工具迁移宣传与团队内实际收益尚未配对测量 | 是否诚实表达未知和推荐限制 |
| P08 | 使用场景缺少会改变选择的关键约束 | 是否识别缺口；需要交互时能否合理收敛 |
| P09 | AI 状态图 / 通用持久执行平台 | 是否区分产品定位、恢复语义与运维成本 |
| P10 | REST / GraphQL | 是否同时评估客户端收益与服务端治理成本 |
| P11 | Kafka / RabbitMQ | 是否区分日志重放、队列路由和交付语义 |
| P12 | 云函数 / 容器服务 | 是否在价格未知时诚实建模冷启动、连接和成本 |

冻结前为每例补齐：完整 query/候选项/约束、参考日期与版本、3～5 个必答问题、可接受的
条件性结论、重大错误示例、参考来源及核验日期、HITL 动作与必要补充文本。
参考答案允许多个合理选择，但必须明确哪些事实和约束不能违反。

候选文件为 `benchmarks/product-baseline-v1.json`。案例与评分规则必须在运行前审阅并记录文件
hash、版本和冻结日期。资料充分/冲突/稀缺标签需通过参考资料核查确认；若不符合槽位，先换题
再冻结。冻结后不因跑分差换题；改题升级数据集。P01～P08 用于诊断与优化；P09～P12 是
保留集。并发验收可以由评审人盲评保留集的串并发配对报告并只返回聚合门禁，优化实施者在候选
锁定前不得查看保留集报告、逐例分数或失败原因。

执行频率：日常代码修改先跑受影响的自动化测试；形成一个可测量候选后，按已确认额度运行
相关开发案例，必要时扩到 P01～P08。候选锁定后才揭示 P09～P12 并做最终验收。完整 O1
基线包含同一 12 例的串行 profile（整条 case 并发度 1）与并发 profile（整条 case 并发度 12），
每个 profile 独立运行 2 次，共 48 个 run。它不是每次编辑的必跑清单；文档和无关修改无需重跑
付费案例。局部试跑不能替代完整候选验收，保留集不能用于反复调参。

## 3. 评分：人工核验内容，程序统计运行

原计划先盲评隐藏版本标签的报告，再查看 Trace 诊断原因。2026-09-16 用户允许助手核验已有开发报告，采用同一必答/冲突 rubric，单列 `assistant_review`、是否盲评、复核与人类校准状态，不冒充人工盲评。六份报告完整阅读及关键声明错误分析不替代全量原子声明分母；引用/来源比例未完成则 unavailable。重大错误、争议引用和所有声称改善的项仍需第二位评审复核并留下依据，未复核/未校准结论标为暂定。首轮不引入付费模型 judge 或默认路径裁判，不改变冻结案例/官方参考文件。

| 维度 | 固定口径与分母 |
|---|---|
| 决策正确性 | 每个必答问题计 0/1/2：错误或遗漏/部分正确但缺条件/正确且说明条件。报告得分为实得分 ÷（2 × 必答问题数）；另列足以改变选择的重大事实错误数 |
| 引用支持 | 核验所有直接支撑推荐、否决候选、关键数字和风险边界的声明，按报告顺序编号并拆成原子声明。每项记支持/部分支持/不支持/无法判断/无引用；完整支持率 = 支持项 ÷ 全部上述声明。无引用仍入分母 |
| 来源质量 | 权威且版本、场景适用的声明数 ÷ 全部关键声明数；逐项记录原始依据、版本/日期和适用条件。官方资料可支持自身功能；性能比较必须核对测试条件，官方身份本身不足以证明优越性 |
| 冲突处理 | 对预先标注的冲突点计 0/1/2：遗漏或错误裁决/识别但解释不足/解释条件差异或有据保留不确定。分母为 2 × 标注冲突点数；无冲突案例记 N/A，同时检查是否捏造冲突 |
| 完成与交互 | 可查询报告数 ÷ 已启动运行数；另列普通报告、受限报告、失败、超时、取消、未结束的数量，合计必须等于已启动数。另报 HITL 触发数、无需人工介入的报告数及各自分母 |
| 耗时 | 逐次记录提交到结束的 wall time、排队、人工等待及 active time；来源不可测时记 unknown。另记每个 12-case profile 的批次 makespan、峰值在途 case 数。按结果类型列中位数和范围，失败运行同样记录 |
| Token 与调用 | 逐次记录已知输入/输出/总 token、缓存命中输入/未命中输入已知小计与完整调用数、usage 完整性、LLM/检索/HTTP 调用和重试。分项缺失为 unknown；仅完整分项且输入大于零时计算命中率。按 node/attempt 分组；Trace 实耗与预算结算/未知/预留分列，预算仍扣总 token，金额沿用 unpriced-v1 unavailable。旧记录不回填，详见拆账协议 |

人工引用支持与系统 `verified/unsupported/unreachable/unknown` 状态并列展示，不能互相代替。
打不开的页面和跨语言不确定性记“无法判断”，不是事实错误。语义质量只对实际产出的报告评分，
同时展示报告覆盖率；无报告不得从完成率分母消失。质量汇总采用逐报告得分平均并附报告数，
引用支持另列整体分子/分母，开发集与保留集分别汇总，不生成综合总分。

## 4. 运行协议

1. 冻结干净 Git 提交、Python/依赖清单、实际模型标识与调用参数、Prompt/资产 registry ID、
   workflow/state/citation/HITL 版本；逐 run 记录 manifest ID。保存非敏感配置白名单和 hash，
   不复制 `.env`、密钥或原始端点。首次基线使用适配后的统一 DeepSeek Flash；保留既有 Prompt、
   输出 token 上限和标准预算，并显式冻结 thinking 配置。旧混合模型结果不充当这个新基线。
2. O1 正式串并发基线确认最多 48 次研究运行（12 例 × 2 profile × 2 次重复），以及包含健康
   检查、重试和可能恢复调用的费用上限。可先批准单次配对 24 个 run，再单独批准第二次重复；
   只有完成两次重复才能宣告并发门禁通过。价格未知
   则记录 unknown，并在执行前采用用户明确接受的调用额度或 provider 硬限额；未使用的次数不自动补跑。
3. 确认服务配置齐备后，运行项目虚拟环境中的
   `python -m benchmarks.run_baseline --health-check`（检索检查，会使用 Tavily 额度）。随后在
   已确认额度内做最小 LLM JSON/tool/thinking 兼容探测；该 health-check 本身不检查 LLM。
   检查通过才启动研究；失败先修复环境。
   中途来源降级则保留失败记录、暂停剩余运行，记录处理决定，不静默绕过健康检查。
4. 使用单实例、单 worker 的 `/api/v1/tasks/*` 完整路径，读取公开 result/observability。
   `benchmarks/product_baseline.py` 是 O1 的 API 驱动采集入口；它支持 serial=1、concurrent=12，
   只输出人工评分模板，不调用 LLM judge。现有 `benchmarks/run_baseline.py` 仍是历史 direct-graph
   工具，不能用于本协议。
5. 完整基线每个 profile 运行两次，每次创建 12 个新任务并预先保存随机种子与顺序。serial
   必须等待一个 case 结束后再提交下一个；concurrent 必须允许 12 条完整任务同时在途，不能只把
   HTTP 创建请求并发后再串行执行。首例或一个单独的未计分 case 用于验证采集；
   若版本和协议未改，该次计入基线。若采集有误，保留记录并显式作废，补跑另计授权次数。
6. 缓存保持默认开启，每次重复从相同知识库快照和独立空的实验产品/检查点数据库对开始，避免
   上次缓存或自学习影响下一次；记录知识资产 hash，自学习设置在前后测保持一致。仅使用实验目录，
   不清空现有用户数据。缓存专项实验后续单列。
7. HITL 只提交案例预冻结的动作和补充内容：P08 预备一次有界补充，其他案例遇 gate 默认选择
   `limited_report`；P08 再次暂停也选择受限报告。人工等待单列。补充文本仅存私有案例输入，
   不放入公开评分表、事件或日志。比较时保持同一交互规则。
8. 不自动重跑失败案例。重试作为额外 run 关联原记录，保留原失败及成本；实验截止仍未结束时
   记录状态和观测截止时间，通过正式任务取消流程收尾。48 次仍是小样本诊断，不能推断总体质量。

标准预算仍为每 run 60,000 total tokens、96 次 LLM、72 次 retrieval、900 秒 active time，
80% 软提醒；这是执行安全上限。测量器必须遵守现有预算、脱敏和安全外呼契约，不能绕过限制。

## 5. 产物与优化判定

PR O1 保存版本化案例文件、评分表模板和最小采集入口；运行后生成独立实验目录，包括
`experiment.json`（版本/环境/健康/日期/顺序）、`runs.jsonl`（任务/run、结果、耗时与用量）、
报告、`scores.csv`（逐项评分及依据）和简短 `summary.md`。路径在执行前确定；本地运行原件
默认不提交，只提交脱敏、人工核对后的必要证据和摘要。保留集报告单独封存至方案锁定。

采集时另保存 `admissions.jsonl`（提交开始/确认创建的即时断点，不含请求正文）及 `usage.csv`。
中断后先核对已有 task/run，不能以缺少最终 runs 行为由重复创建。记录的 running 峰值只是
轮询时观察到的下界，不是全时段精确并发数；HTTP 在途峰值不能替代它。无配对报告时质量门禁
为 unavailable、不通过，失败行不用伪填质量零分。P08 不强制因缺少用户约束触发 HITL；只按已有
证据不足 gate 执行动作，并评价条件性结论。

### 并发效果门禁

以相同数据集 hash、模型/资产配置、知识库快照和 HITL 规则，对 serial 与 concurrent 的同 case、
同 repetition 做配对比较。门禁不是性能压测，也不改变单实例/单 worker 部署约束；它验证当前
实现同时调度 12 个 durable run 时不会因 LLM/检索并发、限流、预算或 SQLite 争用显著损害结果。

- 并发完成数不得低于串行；并发不得增加重大事实错误。
- 决策正确性、引用支持和来源质量的 12 例均值相对串行下降均不得超过 5 个百分点；冲突处理
  均值下降不得超过 10 个百分点。
- 任何 case 的决策正确性不得下降超过 20 个百分点；下降超过 10 个百分点的 case 最多 2 个。
- 比较完成率、失败/超时/限流、重试、unknown usage、LLM/检索调用、token、active time 和批次
  makespan。usage 不完整时保留 unknown，不声明 token 一致或节省。
- 两次重复均通过才算通过。若仅并发失败，先归因到 provider 限流、全局/节点并发门、连接池、
  SQLite 争用或调度策略；不得通过挑选成功报告或放宽评分掩盖问题。

基线后将问题归入需求理解、检索覆盖、来源适用性、冲突处理、结论推导、引用/报告表达、
运行环境七类。按“是否改变决策 × 影响案例数”排序，再估算修复成本，选择 1～2 类；一次
实验只改变一个主要因素。每个假设写明受影响案例、目标指标、预期机制和回退条件。

优化前冻结验收门槛，默认采用：

- 质量优化：至少一个目标案例在两次运行中都达到预定改善项，其他开发案例的逐例均分不下降；
  无新增重大事实错误，引用支持率与完成率不下降。不同目标需在改代码前写明替代门槛。
- 效率优化：相同案例两次运行均值构成配对值，逐例节省比例的中位数至少 15%，且正确性、
  引用支持与完成率不下降；token 不完整时不能声称 token 节省。这是本轮决策阈值，不是统计显著性。
- 候选锁定后揭示保留集基线，并运行同集候选版本各两次。任一重大错误或质量退化即不通过；
  若据此继续调参，该集转为开发集，下轮另建保留集。
- 前后测原则上在同一 7 天窗口，配置与知识资产相同、仅包含声明的变更；间隔超窗、模型或
  来源状态显著漂移时重新确认配对基线。证据混合或两次表现不一致就记“尚未证实”，追加运行
  必须计入新额度，不能只挑成功报告。未达门槛不合入优化，保留实验结论。

## 6. 交付顺序与完成标准

**PR O1：真实案例、串并发基线。** 冻结 12 例、人工评分依据、运行协议和 API 采集器；完成
离线验证后，在批准的额度内各执行两次 serial=1 与 concurrent=12，记录基线、并发差异、失败
分类和一个优先优化假设。环境或授权未就绪时
明确标记“实测待执行”，不能宣告基线完成。

**PR O2：首轮针对性优化。** 按冻结假设实现、补回归测试、完成前后测与保留集核验；提交
改善/未改善结论、成本变化和剩余问题。执行受影响测试、完整仓库验证与独立代码复审。
每个优化 Phase 最多两个实现 PR，后续轮次由结果决定。

阶段完成意味着当前真实案例集上的效果与成本有据可查，首轮假设得到支持或被否定；不能将
未改善包装为提升。预算调档、扩充样本和面试展示在本轮结果审阅后另行决定。
