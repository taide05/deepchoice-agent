## 1. 评什么

以用户的选型问题为单位，分别记录运行完成、可用性、依据与错误。主要结论不由引用计数、
测试数、篇幅或模型自评决定。每例冻结3–6个必答项和可接受的条件结论范围，不预设唯一赢家。
只评原始需求；普通选型不能因提到“迁移触发”就被额外要求交付完整双写/切流/回退方案。
报告主动给出高风险操作时，该操作仍需接受安全核对。

每份报告记录下列二元检查及理由；信息不足时记录unassessable，不能当作通过：

| 检查 | 通过条件 |
|---|---|
| 约束与回答 | 不违背硬约束；回答所有影响选择的必答项，或者给出具体缺口及其决策影响 |
| 有用建议 | 给出有理由的选择/条件分支、关键取舍及可观察的改变条件；没有以通用清单替代回答 |
| 决定性依据 | 直接影响选择、排除候选、风险判断的事实有适用的保存来源；推论明确前提且不越过来源边界 |
| 不确定性 | 未知和场景假设明确；资料不足时说明能答/不能答的部分，不夸大确定性也不无差别弃权 |
| 一致与安全 | 摘要、分析、结论一致；不捏造能力、实测阈值或来源，不给危险操作保证 |

五项均通过、且无下述关键错误才记为“可用且有据”。结构化字段不优先于实际正文：
Winner为空但条件分析完整可以通过；字段为completed/verified但正文误导仍不通过。

## 2. 错误分级与评审锚点

- **关键错误**：违反硬约束、捏造决定性能力/来源/测量、反转关键因果或适用条件、缺依据
  却作关键排除/保证，或给出可能丢失数据/破坏安全的操作。即使总建议碰巧合理也必须记录。
- **重要缺口**：用户无法据此理解当前选择或下一验证点；核心问题缺答、决定性事实没有
  对应来源、推论缺前提、局部降级清空关键解释。记该项不通过，不等于全文无用。
- **一般问题**：重复、格式、非决定性旁支引用或不影响结论的措辞。记录即可，不单独否决
  整份报告，不在最终测量后把它升级为新门槛。

例如“无法排队的多写者适合客户端/服务器”被写成“只有这种情况才应选它”，需要结合
它是否改变本案选择判断严重性；不能因出现“只有”就机械计错。SQLite低运维结论本身
可能合理，但标记为模型分析不能免除其关键事实依据。术语未逐字出现、未做实际部署，
均不自动失败。Q0用已有报告固定这些边界的正反锚点，减少评审漂移。

每条决定性判断保留report行号/片段、原引用、保存证据定位、前提、支持/部分/不支持/
未知及问题等级。事实、来源支持和推论是否合理分开检查；新查资料不能回填原引用支持。
覆盖所有决定性判断即可，不重建无关逐句原子台账。只有完整声明分母才可公布完整引用支持率。

## 3. 数据与暴露边界

- 开发集4例：原P01、P04、P08及已有P02。保留原请求、硬约束与业务问题；从原冻结
  数据逐例提取，复制为新协议的版本化投影，记录原ID/hash。旧fixture/评分不改。
- 最终集8例：上述4例加4例新保留场景；至少覆盖4类技术取舍，包含明确需求、缺输入的
  条件决策和运行/数据风险。新例不能只是已练案例替换技术名字，也不能事后删掉难例。
- 旧P09–P12的参考边界已在先前工作及本次文档审查中暴露，不称新鲜保留集；原历史
  隔离记录不追改。本轮新保留题、参考依据与逐例反馈由未参与实现的独立评审准备和保管，
  实现者在候选锁定前只看覆盖类别、数据版本/hash，不读题目或答案。
- 保留集参考答案与评分不得注入检索种子。开发材料可以用于定位，但须披露知识种子
  与开发案例的关系，避免把记住固定来源称为泛化。所有场景使用同一冻结来源政策。
- 案例/rubric先冻结，报告后产生。数据缺陷先记录；发生改变则版本化并使相关比较失效，
  不在看到低分后删改题。保留集反馈一旦用于实现，该集转为回归集，不再声称未见。

## 4. 分阶段测量与研究分配

Q0只做已有证据审阅、局部离线回放和案例冻结。它不证明模型质量，也不产生新研究。

开发最多12次：先在相同请求/种子/配置下收集冻结工程基线4例与首个候选4例，保留完整
8格；另4格用于有实质改动的后续候选。旧版本/异窗口报告仅用于诊断，不混入当前对照。
能合法复用同窗口、同请求且身份完整的基线时少跑相应格；不重启旧停止根。前后观察应
处于不超过7天的窗口，记录外部材料变化；单次开发对照是方向证据，不是稳定性证明。

开发晋级要求：4例都有可评的结果，候选无关键错误；至少3/4“可用且有据”，目标
缺陷在所覆盖案例中减少，已有通过例不发生实质退化。若基线已达到上限，候选应至少
保持质量且解决已定位的重要缺口；不为制造增益强改。未达到时返回定位，不触碰保留集。

最终检查固定8例×3次=24格，串行、同一候选、同模型/参数/依赖/知识政策，保存运行顺序。
采用预先固定的交错顺序，避免把某一例全部放在网络最好时段。每格仅一次整例提交，
产品内既有有界重试照常计入调用预算。代码/提示变化后，不能拼接不同候选的24格。

**最终验收门槛（本项目的前瞻工程目标，不是行业标准或统计置信保证）：**

- 至少23/24格完成可查询且正文/导出一致的结果；预先规定的HITL按原请求的固定上下文
  回答，不能由评审临场提示答案。缺必要用户输入且无法按冻结规则完成的格记未完成。
- 至少22/24格“可用且有据”；开发部分与新保留部分各至少11/12，每例至少2/3。
- 所有已产出的最终检查报告中，关键错误为0；一般措辞问题不要求清零。
- 同例三次的结论无无法由证据/输入变化解释的实质矛盾。合理条件分支等价不要求逐字相同；
  每例仅一次的观察不能作为重复稳定性。未完成格仍留在24格分母中。
- 没有未解决的安全、预算、生命周期或身份异常；必要工程验证与独立内容复核完成。

24次观察只支持“小规模固定8场景上的重复验收通过”。不能外推“真实用户可靠率≥90%”
或统计显著改善，不与旧300-case、12-case smoke或旧引用分母合并。

## 5. 评审过程与可比较性

沿用助手主评与独立助手复核，明确记录assistant_review、是否盲评及未做人类校准。
Q0至少对正/负/临界3个锚点对齐判据；之后冻结等级，不能在不同版本上用不同宽严尺度。
开发对照隐藏版本并随机报告顺序；评审只读请求、报告与原保存证据，先锁判断再看Trace。
无法完全盲评时如实标非盲，不能包装成独立实验。最终24格全部核对决定性依据，独立复核
所有关键/争议项以及最终通过结论；分歧未解决时该项不能记通过。

这种复核提供助手评审下的质量证据，不冒充领域专家或用户验收。不新增默认路径LLM裁判，
不以自审分数作最终质量标签。若未来引入自动judge，须先单独校准和修订资源计划。

## 6. 记录、异常与停止

每批记录数据ID/version/hash、候选和基线commit/资产/manifest、环境/种子、调用预算、
时间、所有准入及未提交原因。运行完成率以全部已提交为分母；另报预定矩阵完成度。
失败/无报告不捏造内容零分，但在端到端可用率中不算成功。受限报告、内容失败、运行失败、
安全停止、证据unknown分开；每例状态与各类缺陷保留，不能只报一个总FAIL。

新研究一律走durable API与新隔离目录。每run沿用60000 tokens、96 LLM、72检索、
900000活动毫秒及当前其他资源边界。预算未知不能填零；准备探测和研究成本分开。
每批最多一次已有有界前置检查：最多4 LLM、20非LLM HTTP（其中最多1 Tavily POST）；
代码/配置/有效窗口兼容时复用，不因普通文档变化重做。前置失败先诊断，不自动再探测。

开发报告内容失败进入错误分析，不自动终止整个质量目标。已正确暴露为unknown/partial的
普通来源故障按冻结矩阵记账，禁止补跑；安全、预算、租约/实例权威丢失、未知提交、身份
漂移或未分类异常立即停止新准入、对账和维修。不得忽略Retry-After或把失败检索变空成功。
旧控制器若把这些类别混用，先对未来运行制定明确矩阵并离线验证，不能临场豁免或回改历史。
最终检查按预定矩阵执行；已确认关键错误或无法达标时可提前关闭整批，剩余格记未提交，
该批不可续跑或改写为通过。后续工作按新证据调整方案，受剩余额度约束。
