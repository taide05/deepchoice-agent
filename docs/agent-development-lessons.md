# 开发教训（可选背景）

更新：2026-10-24。本页不再是必须先读的接手约束。用户与 dsh 负责后续路线，
当前交接见 [这里](next-session-product-optimization-handoff.md)。

此前推进耗费大量精力在工程门槛、计划与重复审查上，局部测试通过经常没有转成有效回答。
Codex 给出的工期依赖未经验证的修复成功假设，不应当作交付承诺。

保留几条有用经验：

- 直接看用户拿到的报告，别把运行完成、测试数量或内部证据数量当作回答改善。
- 代码过滤、来源不足与模型遗漏可能同时存在；有证据就动手修，不要求先证明唯一根因。
- 旧失败可以反复用于开发，不必每次换新题。未见成绩另行标识即可。
- 模块多不等于必须合并，代码旧也不等于必须保留。以效果和维护成本选择简化方式。
- 能复用的验证不要重复做；提示/格式的小改动不必触发全工程审计。
- 用户等待和暂停不算主动工时；不把每次失败转化成新审批、日志和门槛。
- 保留用户工作、原始结果与实际用量；失败是工程反馈，不是禁止继续开发的规则。
