## 下一轮接手顺序

1. `git status --short --branch`，读当前提交和未提交改动；核对当前代码、
   `AGENTS.md`、本页、[状态](o1-execution-status.md)及必要运行契约。旧 dsh 工作树、
   历史交接和远端跟踪分支不能覆盖当前 Git 事实。远端未成功刷新时标记未核实。
2. 对照完整用户使用链路列出可执行检查：提交与澄清、任务进度/SSE、必要 HITL、
   成功/失败/恢复、可查询结果、Markdown/安全 HTML/PDF 下载。区分自动化证明、
   人工 UI 证明与未测项；旧工程测试通过不等于本轮实际 UI 验收。
3. 离线盘点活动数据流和测试资产。按阶段列输入、输出、消费者、可能的信息损失、
   证据与未证实假设；对多个问题同时排查，优先处理共同原因。给每个修复包写清
   删除/合并/必要新增的替代关系及安全、引用、预算、恢复、兼容保留边界。
4. 实施中用固定材料回放、节点级检查和相关回归；代码及测试精简同包。完成一批后
   冻结代码/配置/依赖/manifest，再运行受影响测试、完整工程套件与契约要求的独立复核。
   仅文档改变可复用仍有效的工程套件结果。
5. 在**另行明确时间与外呼额度**后，独立准备并封存全新内容验收题、必答项、来源
   政策、运行顺序、候选身份、上限和停止线；一次集中运行预定完整报告批次。
   逐份保存原件和来源，先评内容再看 Trace/成本；失败照计，不能挑最好、改题回写成功。
   对旧题做相似性核对，主题换名或改写措辞也算重复。无需在本页预置新题或固定四例数字。
6. 分别交出工程状态、内容状态、完整使用链路、测试资产变化、成本/耗时、风险及
   可回滚提交。只有原始报告达到预先冻结的内容标准才称“可用报告”；若未达标如实交付。

下一轮的接受准则仍采用[评估协议第 2 节](product-effectiveness-optimization.md#2-报告内容判定)
的语义维度，但**不用 Codex 时期任何旧题或旧分母**。独立准备者应在实现者不能据题
定向修复的条件下创建全新题，按实际需求覆盖不同技术取舍、硬约束、证据适用性和
需求缺项。题目暴露后立即转为已见材料；新的保留集需另行补充。历史冻结物保持原样，
只用于审计旧结论，不能以改写、换编号或重跑取得新的通过率。

## 约束冲突的处理

- **授权**：旧十小时与八小时计划都已结束；旧“持续付费授权”不提供下一轮额度。
  当前允许离线审计与文档交接。新代码/运行任务的范围按用户后续委托决定；付费研究
  需明确新的上限及冻结身份，最终 24 继续封存。普通已授权工作不必逐提交求确认。
- **减法与安全**：删并重复判断优先，但不得删除 provenance、引用 `unknown`、安全
  外呼、脱敏、预算 fail-closed、CAS/fencing、事务/恢复或仍有消费者的兼容适配。
- **验证成本**：改动期间跑最小相关检查，冻结一次跑完整必需验证；代码、测试或运行
  条件再变化时才重跑相应门槛。报告测量采用预冻结批次，不能逐补丁消耗整例。
- **文档**：本页负责经验与接手顺序；`AGENTS.md` 负责全仓硬约束；路线负责目标；
  协议负责内容判定；状态负责已发生事实；运行契约负责系统边界。旧计划正文仅供
  历史核对，不能从其“下一步”或“OPEN”推导新准入。
