# 整体质量优化：推进与维修规则

更新：2026-10-10。范围见[路线](current-roadmap.md)，度量见[评估协议](product-effectiveness-optimization.md)，
事实和余额见[状态](o1-execution-status.md)。本页取代旧单场景逐次停线方式。

## 1. 按共同原因形成可检查的修复批次

唯一活动安排为[路线第1节八小时计划](current-roadmap.md#1-要交付什么)，计划ID
`delivery-eight-hour-20261010-v1`。旧十小时计划已归档；硬上限与N4收束时间不自动延长。
方法优先级见[AGENTS.md](../AGENTS.md#high-priority-execution-rules-subtraction-first-2026-10-10)。

排查以活动代码与数据流为主线：输入输出、实际消费者、具体过滤/转换/重建/覆盖、重复
判断及权限边界。已有失败作反向核对和回归，不逐例叠补丁，也不从头重做历史全仓审计。
模块有独立职责就保留；来源选择与问题判断可以分离，之前合并没有证明质量收益，
不能把模块数减少当成果或预设继续合并。交接前代码仅供具体逻辑参照，不假定旧实现完美。

先在现有卡中记一个问题批次：用多个已保存、已暴露的固定请求/来源，逐阶段列原始需求、
实际消费者、输入输出和首次损失位置，区分材料不足、模型遗漏、代码过滤、引用未知、
渲染损失。把已确认的共同原因合成有限修复包，写明拟删并的旧处理、保留边界、预计
完整回答收益和反例；不把互不相关的猜测塞进同批。替身只证明结构/传递，真实模型与
来源适用性仍需真实证据确认。无需另造审批或审计流程。

默认删减、合并代码逻辑、复用现有实现。新增分支、关键词表、提示约束、例外、兜底或
调用只有在共性阻断已确认且无法更简单解决时才允许最小实现并说明依据。必要核验与恢复
校验有不同信任边界时保留；未知不等于假，也不等于有权作为确定依据。

代码精简与测试精简同包：删除退役逻辑对应测试，合并重复准备和无独立故障价值的覆盖，
保留不同安全、事实、预算、CAS/恢复、兼容负例；不把参数藏进循环制造数量下降。
生产精简是主线，测试不另开专项。不能仅改测试断言让有害行为变绿；行为改变需相关
回归，文档同步，完成的改动必须可追溯提交。

工程候选不等于质量通过。实施中的反馈用固定材料回放、节点级和相关回归；不要把
每一处修改接一份完整研究报告。完成一批共同原因修复并冻结代码、身份、请求与停止线后，
才集中运行一次完整报告批次。当前两次整例诊断已用完；N2若在多个已暴露问题上没有
固定材料改善，不启动N3。N3四份报告保持原内容标准，原件全部保留；来源状态、局部
恢复和净删行数不能代替独立内容判断。连续两个实质方案无收益，结束该机制。

## 2. 控制工作量、验证与等待

- 一次推进一批有共同原因的处理问题，允许改动相邻环节；不要逐个修复逐个跑整例，
  也不要把无关改动混入同批。每30分钟或阶段出口核对收益与时间；具体阶段
  出口、机动、准入/冻结/收束检查点由路线唯一维护，本页不复制另一张时表。
- 相关测试在实施时运行。最终代码/测试冻结后跑一次完整所需验证；仅文档/注释/结果
  更新复用有效通过。生产、测试或执行条件变化则重跑受影响检查及全套，不能省略交付门。
- 冻结前用离线/固定材料回放检查因果和故障边界；完整报告只在批次出口按冻结身份运行。
  工程全套与独立复核按交付契约执行，不把未验证候选宣称完成。
- 复用已有采集器、预检及独立准备材料。冻结的预检须覆盖实际LLM与检索且身份仍兼容；
  未运行的准备spec不能冒充准入绑定，诊断后最终批次起始账本应按实际重新冻结。
- 本轮整例研究新增总上限10：两次必要诊断231/232、首次集中检查233–236、
  实质返修后一次重检237–240均已结算，研究累计240，从230起本轮已用10/10。
  不为逐处反馈重置诊断额或跨用途借用；最终24不动。单次受控模型
  诊断和预检调用另记调用/token，不伪装零成本或整例成功；每批均遵守冻结预算和硬停点。
- 最终两类未暴露请求仍由独立准备者保管；受开发反馈影响即标回归。若额外返修暴露
  了所有最终请求而需重新检查，独立准备者替换必要未见类，冻结新版本并保留旧失败；
  无时间或无有效证据时记未达标，不改题后回写通过。
- 运行成功、输出一致、成本和内容分别记账。价格未知保留未知。发生安全/预算/权威
  异常、身份漂移或未知提交即停准入并对账，不能通过重跑覆盖失败。
- 需要等待时明确对象与期限；普通阶段转换继续已授权工作。用户明确暂停后，代码修复、
  测试和整例研究均停；后续仅授权文档整理不等于恢复产品执行或研究准入。八小时硬限
  仍适用，文档工作计入有效工时；到限如实收束，未完成交付不自动获得新预算。


## 3. 失败、维修与恢复

| 情况 | 处理 |
|---|---|
| 内容错误/关键缺答/引用错配 | 记录影响及共性原因；开发批按预定矩阵完成后决定候选，不把一个失败扩展成项目全败 |
| 一般表达问题 | 记录；不单独开新实现轮、不抬高冻结门槛 |
| 可归类的外部故障 | 区分HTTP与逻辑结果，遵守限流/超时并保留降级；不重复整例来覆盖失败 |
| 运行/采集实现缺陷 | 停止相关准入、保存证据并维修；必要故障测试和独立复核后，按新身份/预算决定未来运行 |
| 安全、预算、身份、权威丢失或未知提交 | 停止新准入，核对任务/预算与两库，不吞异常继续；收齐证据后处理根因 |
| 数据集或评审有缺陷 | 先判是否影响决定，保留原结果；须修订则版本化，不能为了低分改题或改标准 |
| 没有净改善 | 放弃该方案、简化或重新定位；保留有效成果和失败证据，连续无收益规则见上 |

中断后依次读Git状态→当前文档→准入记录→task/run终态与服务归属→配对数据库→兼容身份
和预算。未知提交先对账，collector缺输出不代表未提交；不能重启旧停止根或直接写生命周期表。
主机/助手中断不清空研究账本。恢复、服务停机、备份保留原授权边界。

## 4. 持续授权与分工

用户的新质量方向包含范围内正常实现、必要维修、验证、评审、文档与本地提交；已有付费
授权持续有效，冻结批次后无需再为普通费用、每次提交或阶段切换提问。预算和供应商边界
沿用当前地图，不从旧OPEN卡或余额推导任意调用。明确越界才集中请求决定并继续独立工作。

需要独立内容评审、保留集准备或契约要求的独立工程复核时，使用独立评审者；内容/工程
复核只读，案例准备只写分配的材料。说明暴露情况与覆盖范围，不冒充人工专家。实现默认单线，必要独立复核不扩展成多团队并行工程。
文档重组可做一次独立一致性复核，重点检查新旧边界、预算算术、冻结证据和可执行性。

不修改外部求职材料，不增加供应商、数据外传范围、生产操作、push/merge/release。
长程目标不是后台定时任务；不自行建立自动化或调度平台。

## 5. 跨会话工程循环与交接

长程目标保存在当前任务中，仓库以本页约束推进方式，以评估协议判定质量完成。
一次提交、一次定位或会话结束都是检查点，不自动结束目标；普通阶段转换无需再次询问用户。
当前助手沿依赖继续下一项已授权工作，直到取得实质成果、遇到真实边界或会话被中断。
原方案失败后依据停止线换机制，保留同一质量目标，不把目标缩成容易通过的局部修复。

### 方向检查

每轮开始、跨会话恢复和转入下一阶段前，先对照用户的核心成果做一次简短方向检查。
同一卡点连续两次返工、辅助工程明显膨胀，或连续只增加规则/文档/测试而未接近用户效果
证据时，立即触发检查；不能因为已有投入或局部测试通过就继续原路径。

以下五项只在阶段出口或上述偏差触发时简短核对；已有事实直接引用，不另建评估体系：

1. **核心成果**：完整默认链路当前缺少什么稳定有效回答能力，它怎样服务支持范围内
   多数场景目标；交付标准需要哪些相应证据？公开四例的单题进展只能作诊断/回归。
2. **当前动作的贡献**：它直接改善哪个用户结果，或解除哪个必要前置障碍？无法说明则撤出当前轮。
3. **卡点的来源**：它来自用户/现行契约/已观察风险，还是助手自行增加的完美化要求？
   区分输入身份、工程可运行与输出质量；核验已明确要求的跨场景泛化，不把逐字确定性
   或无限问题覆盖变成新验收门。
4. **最小安全路径**：能否删减、复用或换实现完成核心成果？只修复阻断当前成果的部分，
   不顺带扩建平台或追求穷尽解释；真实安全、预算、数据和保留集边界必须保持。
5. **本轮出口**：下一项可执行动作、它应产生的证据，以及达到什么条件就结束辅助维修、
   返回主线。结论明确为继续、收缩范围或重新定位，并说明依据。

方向检查用于调整工作，不形成逐轮用户审批。独立评审的建议须判断其对应的具体风险和
核心目标；必要问题修复后即返回主线，不把所有改进建议都升级为阻断项。
工程卡点的返工次数与“两种实质质量方案无跨场景净收益”的停止线分开记录，不能互相
替代或借重新命名规避停止线。检查本身不计为质量进展；检查后执行下一项安全动作。

本次交付只维护一张本地执行卡`notes/delivery-current-work.json`；
旧`notes/quality-selection-current-handoff.md`与`notes/delivery-resume-point.md`仅保留失效
提示，其原文已在本地归档；不得把旧ACTIVE、计时或下一步当作现行指令。
秒级工时以`notes/delivery-pause-state.json`为准。详细原始证据留在对应outputs/notes目录；
任务卡引用维护文档与证据位置，不复制历史叙述，也不成为新的授权来源。
任务卡只记录当前阶段、剩余秒数引用、已确认问题、下一个动作、验收/停止条件及证据位置。
历史流水不追加到活动段，已完成动作不继续写为待办。任何阶段调时都同时核对路线总额、
当前状态及本地执行卡；保留实际用时和历史研究账本。

恢复时先按第3节核对现实状态，再读取任务卡接续下一动作。未核实的旧“运行中”标记、
聊天承诺或超时都不能作为仍在运行/已经停止的证明；已准入但结果未知时先对账。
旧任务卡中的费用/授权限制若已被当前用户指令覆盖，更新当前卡并保留原始账本，
不把过时限制重新变成审批门。任务卡不能覆盖评估协议、冻结产物或真实Git状态。

每次续接先判断上一轮是实质进展、对已确认活动句柄的有效等待，还是无进展。
新增规则、状态复述和未执行计划本身不算质量优化进展；无进展时执行下一个安全动作，
不重复同一定位摘要。阶段成果必须连同证据、下一动作和未解决风险写入检查点；
已完成的仓库修改按AGENTS.md提交，任务卡和原始运行资料留本地。
可检验假设足以进入设计，不额外要求多个案例必然由同一个代码bug导致；
工程验证和跨场景真实结果再决定假设是否成立。

只在质量终点被完整证明、用户明确暂停，或授权/预算/保留集暴露/安全/发布等真实边界
需要用户决策时交接控制权。暂停期间只处理用户重新明确授权的范围；达到其他边界前完成
所有不依赖该决定的工作，并提交具体可审产物。
最终回复是检查点摘要，不是自动宣告目标结束；没有达到质量终点时保留活动目标。

## 6. 完成与资源边界

区分“工程验证通过”“候选跨场景质量改善”“固定八场景稳定性验收通过”与
“支持范围内多数场景能力获得广度验证”。旧失败不回写为通过，新失败不抹去已交付能力。
评估协议的八场景门槛、独立复核和可追溯交付只能支持相应固定场景结论；多数场景目标还需
按路线预先冻结并完成代表性广度验证。新增验证设计须先确定支持范围、抽样框架、类别/权重、
独立保留样本、成功分母/阈值、重复性、关键错误与成本上限，不能看报告后改门槛。
保留题用于改进即改记回归集，最终24格在现行前置门槛达成前仍封存。
若当前资源不能再支持合格测量，报告已知效果、未解决缺陷与所需的具体范围决定；
不降低标准、隐藏失败、无限重试，也不以预算耗尽冒称完成。
