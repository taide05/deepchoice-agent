# 整体质量优化：推进与维修规则

更新：2026-10-03。范围见[路线](current-roadmap.md)，度量见[评估协议](product-effectiveness-optimization.md)，
事实和余额见[状态](o1-execution-status.md)。本页取代旧单场景逐次停线方式。

## 1. 每轮形成可检查的成果

每轮围绕一个共性质量缺陷，先留下5项简短记录：问题及影响案例、现有证据、预期改进、
最小改动范围、验证与停止条件。写入当前状态或本地工作记录，不再新增一套长期执行文档。
完成“定位→实现→局部验证→必要整体验证→真实对照→评审→本地提交”，按依赖安排顺序；
模型质量只有真实报告能确认，纯结构/渲染问题先用既有数据回放。

优先改动缺陷发生的环节。来源缺决定性信息时不继续改输出措辞；分析在绑定后丢失时
先核对接口与转换；有依据的结论被通用规则抹掉时检查规则适用范围。允许删除重复步骤、
整合相邻模块和必要局部重构，变更必须保留安全/预算/生命周期契约并有真实回归价值。

同一缺陷连续两种实质方案无收益，结束该方案路径并重新定位或试验更简单流程。
不得以改版本名、加更多提示约束、换问题或反复抽样继续原循环。新方案需要说明不同机制，
通常在已有授权内推进；这不是每两次都要求用户确认，也不是自动宣告整个目标失败。

## 2. 控制工作量与等待

- 工作粒度是“一个缺陷族的用户效果”，不以提交数、测试数、文档数衡量进展。
- 一次只推进一个实现包；调查到可验证假设后开始实现，不要求先穷尽所有技术债。
- 实施过程中只跑相关测试；生产/测试冻结后跑一次完整CI所需检查。只改文档或记录结果
  时复用有效完整验证。工程测试不替代内容评审，真实研究也不替代回归测试。
- 付费测量在有实质候选或需排除关键假设时进行，不要求每次代码提交跑研究。精确登记
  每次整例准入、调用和累计上限；不能仅因新增额度需要明确授权就尽量避开必要的真实评测。
  先完成可复核的冻结和离线防故障检查，在授权范围内按质量问题所需运行，再依据真实报告
  内容决定下一轮。
- 每个成果点说明“用户能得到什么变化、证据、剩余缺口、下一动作”；耗时无法估准时
  说明具体等待对象和停止时点。长调用有已有期限，不让停机服务或结束批次显示为运行中。
- 维护状态只保留当前候选、问题、预算、下一成果和证据链接；详细流水放本地或历史归档。

## 3. 失败、维修与恢复

| 情况 | 处理 |
|---|---|
| 内容错误/关键缺答/引用错配 | 记录影响及共性原因；开发批按预定矩阵完成后决定候选，不把一个失败扩展成项目全败 |
| 一般表达问题 | 记录；不单独开新实现轮、不抬高冻结门槛 |
| 可归类的外部故障 | 区分HTTP与逻辑结果，遵守限流/超时并保留降级；不重复整例来覆盖失败 |
| 运行/采集实现缺陷 | 停止相关准入、保存证据并维修；必要故障测试和独立复核后，按新身份/预算决定未来运行 |
| 安全、预算、身份、权威丢失或未知提交 | 停止新准入，核对任务/预算与两库，不吞异常继续；收齐证据后处理根因 |
| 数据集或评审有缺陷 | 先判是否影响决定，保留原结果；须修订则版本化，不能为了低分改题或改标准 |
| 没有净改善 | 放弃该方案、简化或重新定位；保留有效成果和失败证据，连续无收益规则见上 |

中断后依次读Git状态→当前文档→准入记录→task/run终态与服务归属→配对数据库→兼容身份
和预算。未知提交先对账，collector缺输出不代表未提交；不能重启旧停止根或直接写生命周期表。
主机/助手中断不清空研究账本。恢复、服务停机、备份保留原授权边界。

## 4. 持续授权与分工

用户的新质量方向包含范围内正常实现、必要维修、验证、评审、文档与本地提交；已有付费
授权持续有效，冻结批次后无需再为普通费用、每次提交或阶段切换提问。预算和供应商边界
沿用当前地图，不从旧OPEN卡或余额推导任意调用。明确越界才集中请求决定并继续独立工作。

需要独立内容评审、保留集准备或契约要求的独立工程复核时，使用独立评审者；内容/工程
复核只读，案例准备只写分配的材料。说明暴露情况与覆盖范围，不冒充人工专家。实现默认单线，必要独立复核不扩展成多团队并行工程。
文档重组可做一次独立一致性复核，重点检查新旧边界、预算算术、冻结证据和可执行性。

不修改外部求职材料，不增加供应商、数据外传范围、生产操作、push/merge/release。
长程目标不是后台定时任务；不自行建立自动化或调度平台。

## 5. 跨会话工程循环与交接

长程目标保存在当前任务中，仓库以本页约束推进方式，以评估协议判定质量完成。
一次提交、一次定位或会话结束都是检查点，不自动结束目标；普通阶段转换无需再次询问用户。
当前助手沿依赖继续下一项已授权工作，直到取得实质成果、遇到真实边界或会话被中断。
原方案失败后依据停止线换机制，保留同一质量目标，不把目标缩成容易通过的局部修复。

每轮只维护一张本地任务卡，复用ignored文件
`notes/quality-selection-current-handoff.md`。详细原始证据留在对应outputs/notes目录；
任务卡引用维护文档与证据位置，不复制历史叙述，也不成为新的授权来源。
任务卡须包含：

| 字段 | 必填内容 |
|---|---|
| 目标与本轮 | 用户效果、当前缺陷族、可推翻假设、所处阶段及下一项可执行动作 |
| 身份 | 工作树/分支/当前commit、未提交文件及归属；测量前另冻结运行身份 |
| 已证实与未知 | 影响案例、结论及证据路径；区分观察、假设、工程通过和质量通过 |
| 验证 | 已运行的检查及结果、对应源码身份、仍欠的必需验证；源码变更使哪些结果失效 |
| 运行与准入 | 活动进程或工具句柄、输出路径、准入编号和剩余额度；无可确认句柄时写待核验 |
| 下一步与停止线 | 直接可执行的动作、完成判据、同机制已测方案数、停止/重定位条件 |
| 真正阻塞 | 需要用户决策的具体事项及依据；没有则写无，不能把普通设计选择列为阻塞 |

恢复时先按第3节核对现实状态，再读取任务卡接续下一动作。未核实的旧“运行中”标记、
聊天承诺或超时都不能作为仍在运行/已经停止的证明；已准入但结果未知时先对账。
旧任务卡中的费用/授权限制若已被当前用户指令覆盖，更新当前卡并保留原始账本，
不把过时限制重新变成审批门。任务卡不能覆盖评估协议、冻结产物或真实Git状态。

每次续接先判断上一轮是实质进展、对已确认活动句柄的有效等待，还是无进展。
新增规则、状态复述和未执行计划本身不算质量优化进展；无进展时执行下一个安全动作，
不重复同一定位摘要。阶段成果必须连同证据、下一动作和未解决风险写入检查点；
已完成的仓库修改按AGENTS.md提交，任务卡和原始运行资料留本地。
可检验假设足以进入设计，不额外要求多个案例必然由同一个代码bug导致；
工程验证和跨场景真实结果再决定假设是否成立。

只在质量终点被完整证明、用户明确暂停，或授权/预算/保留集暴露/安全/发布等真实边界
需要用户决策时交接控制权。达到边界前完成所有不依赖该决定的工作，并提交具体可审产物。
最终回复是检查点摘要，不是自动宣告目标结束；没有达到质量终点时保留活动目标。

## 6. 完成与资源边界

区分“工程验证通过”“候选质量有所改善”“最终稳定性验收通过”。旧失败不回写为通过，
新失败不抹去已交付能力。只有评估协议的最终门槛、独立复核和可追溯交付齐全才完成目标。
若当前资源不能再支持合格测量，报告已知效果、未解决缺陷与所需的具体范围决定；
不降低标准、隐藏失败、无限重试，也不以预算耗尽冒称完成。
