# 实施方式

更新：2026-10-24。以尽快改善真实回答为主，用户与 dsh 直接协作。

## 连续推进

在当前委托与预算内，dsh 自行完成必要的定位、实现、测试、运行、修正和本地提交。
不因每个子步骤、一次内容失败、复测或阶段切换反复请求许可。旧轮数和单例停线不延续。
已有授权不足、存在未知提交或实际数据/安全风险时，说明具体问题，再确定后续动作。

## 最短有效工作

- 先利用当前代码和失败材料，选择能改善用户报告的修改；不要求全仓审计或完备因果证明才可尝试。
- 可简化不必要处理，也可做必要新增；短说明交代改了什么、为何有帮助即可，不另写替代关系审批表。
- 开发题可以复测，保留不同版本结果和实际用量。初期以少量典型问题看收益，需要测稳定性时再扩大。
- 普通内容失败、来源缺失或小格式问题不自动停止整个开发；不要把剩余限制都变成交付阻断。
- 开发中修改评分范围可以由用户与 dsh 商定，记录新版本；旧评分保留。正式宣称未见成绩时才遵守相应隔离与固定口径。

## 验证与评审

普通局部改动跑相关回归，并直接读报告确认回答改善。较大集成、运行时/安全/持久化变更及
发布候选按风险安排完整验证。独立复核用于高风险、争议点或需要可信比较的结果，
不是所有修改的常规多轮关卡。纯文档改动检查内容、链接和 diff 即可。

不要靠关闭引用真实性、安全 fetch、费用计数或数据一致性换速度。产品分析的表达和筛选规则
可以调整；语义合理的条件回答不要求唯一 winner 或每一项旁支都完整。

## 运行与恢复

一次委托可覆盖多次开发运行和复测，在总额度内连续执行。账本跨重启累计；未知提交先核对
已有任务，避免重复派发。用户暂停时留下当前任务/修改/运行状态，恢复后接续，不重做已完成工作。
普通内容失败与预算/安全异常分别处理。当前额度事实见状态，不沿用旧计划中的“余额”。

## 交付

优先交付可运行版本、原始报告、实际指标和简短说明。演示与说明可提前准备，不等全部正式评测
完成才开始；未测项照实写。用户与 dsh 决定何时投递和需要补足哪些指标。
每次交接保留可追踪本地提交，不改写历史或覆盖用户材料。
