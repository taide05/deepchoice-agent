# 产品优化执行与协作规则

更新：2026-09-21。适用于当前产品优化任务，目标以 [任务地图](current-roadmap.md)为准。
本文件把复盘结论变成执行规则；不启动服务、不放宽安全、不代替付费实验的冻结协议。

## 1. 复盘依据与结论

本轮分页查阅两场会话“产品效果优化”“产品效果优化-第二场”的可用用户消息/最终回复，
直到工具返回历史起点，并对照 Git 提交、当前代码身份和维护证据。部分历史 turn 没有可读
消息或只含截断工具记录，因此不声称逐条审计全部对话，也不编造确认次数、工时占比或根因统计。
此次没有读保留集正文、原始凭据或新增网络事实核验。

| 观察 | 证据及反证 | 改进 |
|---|---|---|
| 阶段号成了交互控制点 | 曾预告“至少还需 3/4 次批准”，连本地 PR3 结项也在内；另有前置通过后再次问已讨论的单例执行 | 阶段门禁由助手检查，正常通过自动衔接；只把实质边界变更交给用户 |
| 一些确认确实必要 | 用户曾明确要求单例逐次授权；安全 CONNECT 适配改变信任边界，后来 110→134 也扩大实耗上限 | 不把所有历史批准一概说成多余；继承有效持续授权，分清当时限制与现行限制 |
| 发现问题后处理有时滞后于任务标签 | 第一场用户指出报告问题未解决，并追问缺引用/网络 unknown 是否进任务；它们随后进入 C 收口并修复 | 每个发现当场登记影响、归属和处置，不等某个未来 PR，也不把“残余问题”当成已安排 |

| 真实工程问题也存在 | 15ca251 租约心跳隔离、09f9b66 查询隔离、d23c948 GitHub GET 中断重试均有实现与回归 | 保留必要修复，不把所有成本归罪于拆 PR 或网络，也不为了快而忽略故障 |
| 最新 521 与之前误判不同 | c46b4ea 的前缀重放证明按冻结 5xx 规则正确停止；外部具体原因仍未知 | 将规则设计与程序缺陷分开讨论；新分类只在新协议生效，不追溯洗掉失败 |
| 已有报告利用不足 | 当前候选已有 12 串行报告，其中 8 开发；正式质量锁分尚未完成 | 先消化现有证据，再决定新采样，不以“下一批跑通”为产品进展替代物 |
| 规划入口重复并滞后 | 40f9266 前 README/路线仍有 60/109、待资格，执行记录已为 90/134；多个历史任务卡含“下一步” | 每种事实一个维护入口，历史材料移出默认阅读集合；只更新职责内文档 |
| 上轮收口方案过度缩减 | 单方向/13-run 被呈现为整个优化终点；历史明确要求成本拆账和 12 路并发效果 | 恢复完整地图，局部实验约束只管本轮，不能抹去其他目标 |
| 主机中断存在但不能统一归因 | 第一场记录蓝屏及 Git 元数据损坏；当前用户说明高后台负载/误关机，轻载未再蓝屏 | 把用户观察作为环境信息；不声称系统诊断证明因果，不将主机中断等同模型/产品缺陷 |

已有正确实践继续保留：隔离实验库、不可变身份、失败与 unknown 分母、holdout 隔离、预算
fail-closed、必要独立复核、可回退提交。问题主要是**成果边界和证据反馈不够清晰，授权被切碎，
异常后过度依赖全批重启，文档入口失去单一职责**。PR 粒度本身不是已被证明的唯一根因。

## 2. 工作单位：一个可验证成果

采用“完整地图 + 一个在做成果 + 问题表 + 滚动选择下一成果”。不再为阶段/PR/小 PR 三层
逐级索取继续指令。开始一个成果时给用户一段简明执行卡：

- 要解决的用户问题及当前证据；预期交付和完成标准。
- 可调整的实现范围、不可改的安全/外传/评测约束、当前可用预算。
- 如何验证、何时停止；下一正常成果是什么。

用户授权成果范围后，定位→实现→测试→必要复审→修复反馈→提交→更新结论连续进行。
可用多个小提交支撑一个成果；不要求一个成果必须一个 PR，也不把 PR 合并/发布包含进本地授权。
每一轮 live 只改变一个主要实验变量；必要的测试、工具修复和文档可以围绕它完成。

## 3. 发现偏离后的处理

问题表放在当前阶段的维护证据中，原始细节留 outputs/；不另造一串永久任务卡。
字段：ID、证据版本/案例、事实或假设、用户影响、严重性、与当前成果关系、处理/后置理由、验证状态。

| 发现 | 助手立即做什么 | 是否等用户 |
|---|---|---|
| 当前成果内的正确性缺陷、必要局部修复 | 登记并调整计划，先定位再修复/测试；涉及生命周期等仍执行原独立复审要求 | 不因跨文件/跨 PR 自动询问 |
| 破坏当前假设的新证据 | 暂停相关实现，重排或取消假设；保留既有提交与实验，说明依据 | 同目标/预算/契约内可自主调整 |
| 相关但不阻塞的真实问题 | 入表，按决策损害和影响面重新排序；给关闭条件，不能默默略过 | 不立刻打断，也不自动扩大本轮 |
| 改产品目标、重大取舍、降低验收标准、扩大数据范围/供应商/信任边界/付费上限 | 完成离线调查和可审阅方案，集中说明选项、推荐、代价和剩余工作 | 仅依赖该决定的动作等待，其他工作继续 |
| 已冻结 live 批次异常 | 按有效规则停止准入、收尾、对账；继续离线复现/归因和规则核对 | 不自动补跑；若授权卡已含有界替代且未越界才可执行，否则集中申请差额 |
| 两次连续付费停止没有有效配对 | 停止相同大批次路径，交付根因置信度/测量设计复议 | 不靠增加总上限继续碰运气 |

“调整计划”不等于改历史评分或输出；不改停止根、原始账本、已经提交的迁移和身份。
一次新增发现只改它影响的目标/测试；不把局部缺陷变成全面重构的理由。

## 4. 用户交互与持续授权

- 进度更新说明新证据、决策及剩余工作；不要每个提交都报一遍“下一步是否继续”。
- 用户说“完成这个成果/这一阶段”时，包括其必要实现、验证、复审反馈、文档与本地提交。
  正常子步骤不再次申请。仅询问会实质改变结果且上下文无法推断的偏好/边界。
- 一个更大成果已获连续执行授权时，阶段检查通过后自动进入其内下一步；“测试门禁”不是人工批准。
  原有预算/外传授权持续有效，不能因会话更换或文档移动要求用户重说一遍。
- 一次请求集中列出真正需要的决定、已完成的准备、准确增量、预期下一段范围；区分外部额度、安全
  信任边界、发布和纯偏好。不能只引用自己写的“须批准”句子循环创造新的审批点。
- 没有新业务决定、尚有授权内可做工作时，继续执行；遇到不可解阻断则交付当前成果与具体所缺条件，
  不只给“已停，是否继续”。有新用户问题时先简答，再继续原目标，除非用户明确改变/停止任务。
- 提交审查和自动化检查可连续推进；push/merge/release、修改未授权外部文档仍需明确授权。
- 2026-09-23 用户将最终人类校准门禁明确改为 GPT-only：固定开发锚点与最终盲评仍须独立复核、
  留下依据和残余风险，不冒称人工判断；不要求用户为每个 run、测试、提交或普通阶段点击批准。

当前授权事实：先前查询/候选/必要上下文可发往 DeepSeek、Tavily、GitHub API、StackExchange API、
arXiv、PyPI/官方来源，经已配置路由传输，并安全抓取公共 HTTP(S) 引用；研究累计上限现为152
（2026-09-23用户批准134→152，当前已用92），完整路线分母与未满足的准入条件见执行状态。
现行12-run局部配对与整合48-run最终/并发路线已获批准，但新协议、种子和执行器尚未冻结，
不从余额推断可立即启动。新执行卡把可连续推进的实现及有界研究整段说明，一次处理真正变化。

## 5. 三类中断与恢复

已报告助手额度中断、主机蓝屏和意外关机三类情况。轻后台未复现是环境观察，
不是内存/驱动/硬件根因证明；机器细节留本地交接，不进入公开产品能力声明。

- **助手额度耗尽**：不查询/反复提醒余额，不为额度缩减质量，不擅自消费 reset credit。
  经常保存可恢复进度和已完成提交，后续按断点恢复。此偏好不取消 paid research 现行152硬上限或单 run 预算。
- **蓝屏/高负载**：沿用已冻结资源启动线和停止线，不把用户的轻载观察当成移除保护的证据。
  重计算、全套测试与真实研究避免同时堆叠；一次一个实验服务；不替用户关闭应用、不擅改系统/代理。
- **意外关机**：视为执行中断。先核对 Git/未提交文件、已创建 task/run/准入日志、实例与端口归属、
  产品库/检查点配对及终态，再决定恢复。不因 collector 没最终行就重新创建任务。
  不自动启动历史实验服务、不改写停止根、不直接写产品生命周期表或恢复备份。

共同恢复顺序：读取当前入口与本地状态→检查 Git→核对已发生的外部副作用→确认身份/预算→
续做安全的离线工作→在兼容且明确允许的边界内恢复执行。若 Git/数据库损坏，需要备份与具体修复
方案；不能把上次损坏的处理命令当作每次通用恢复脚本。
不建设新的调度平台；优先使用现有 durable 生命周期、collector 记录和本地交接。

## 6. 验证、文档与收口

- 先相关测试，代码/契约/测试冻结后跑一次完整必要验收；仅文档/结果记录变化不重复全套。
- 语义改进用真实内容评审与配对证明；离线测试通过不替代内容质量。
- 保留产品候选、控制器和测量协议三种身份；影响产品兼容性的变化须重新绑定产品身份并按现行新协议完成配对 P01 回归门，不自动追加独立单例资格。
- 主动检查“是否仍在解决用户问题”，而不只核对“本 PR 勾选完了吗”。
- 完成时交付可追溯提交、验证、效果/限制、问题表状态和下一正常动作。达到产品完成标准即可停止；
  没达到则清楚标记未达标，不通过继续加文档制造完成感。

本文是后续协作规则；不要求用户重新批准其中的常规只读、离线修复、测试、文档和本地提交。
实际新执行以用户给出的成果任务和有效实验卡为准；本会话按要求完成交接后结束。
