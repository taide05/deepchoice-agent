### 7.3 最小实施契约

**A. 配对适配，不另建研究算法。** 在真实 source evaluation 完成后、冲突检测前留存有界共享
证据与失败状态，内容/身份 hash 在两臂实际输入处核对。仅保存消费者所需的允许字段；不读取
LangGraph 私有数据库，不把 RunContext、租约、秘密或完整私有状态写入公共结果。候选继续走
当前产品链路；基线用相同 manifest 模型/参数、相同有界窗口和当前综合实现，无冲突、自审或
失败后语义重写。共同引用绑定、安全边界和渲染复用；可能产生外呼的验证同样预算化并分臂记账。
不通过 `run_manifest=None` 激活旧提示/纠错分支，也不伪造运行租约来获得预算。

现有 LLM helper 为一次逻辑生成最多3次传输尝试（2次重试，SDK重试0）。应明确继承相同传输
失败策略；“一次综合”不等于只记一次实际请求。共享来源评分本身可能调用模型，归 shared；
候选的冲突/自审为增量。若发现实际路径还会改写/扩充来源，先处理公平性，不用不同输入继续跑。
基线必须有实际生效的派发前资源守卫；裸调 helper 不是实现。此适配是待完成工作，尚未验证成功。

**B. 收拢现有批量工具。** 在 `final_batch.py` 及既有 collector 上补校准 split、配对身份、
授权清单与实际资源上限、resume 对账、报告 hash 与多评审绑定、协议指标汇总。来源/执行
失败可计量，预算/身份/未知提交失败必须停止新准入。不得只修改 JSON 中的 `authorized`、
`eval_ready` 就越过实际核验；未结算提交先用产品状态对账，不删日志后重发。无报告失败保留
在 S，不能因基线未执行而从共同计划 N 消失；各臂与完整配对子集分别列分母。

**C. 数据与评审。** 保留分层，删除“唯一候选对即独立需求”的假设；每题明确真正影响选择的
少量必答项，不扩成完整部署审计。参考允许条件答案和证据不足，不强填唯一 winner。来源的
官方性、版本、日期和适用范围逐项判定，未见资格由独立准备/历史查重确认；看过结果的题
不可挪回正式集。代码锁定前实现者只见类别/契约，参考不进入研究/检索缓存/学习文件。
复核者类型诚实标注；助手独立复核仍是助手评审，不宣称人工/专家校准或0计算成本。

**D. 一次真实使用走查。** 使用预先选定的校准任务走提交、进度、需要时的澄清/HITL、结果
阅读、来源跳转及 Markdown/PDF 导出。复用已有原始产物，不为演示追加研究或手修报告。
未触发的异常/恢复分支沿用离线契约证据，单列未实测；不做新UI工程。最终交付附一个可复算
指标表、架构/取舍说明、原始成功与失败示例、启动步骤和简历事实草稿；不擅自改外部简历或push。

### 7.4 最后一轮的执行顺序与停止点

1. **准备与开发初测**：关闭 A/B 中的测量阻断，冻结开发执行身份；独立准备12个开发需求。
   校准12题和正式120题由隔离角色准备，共144个有效需求，参考不进入产品输入。先实测当前
   维护候选，不能把实验树旧失败直接当作当前根因。
2. **最多两批共性改进**：开发初测按“需要的证据→实际获得→实际送入模型→回答→绑定/核验→
   展示”定位损失，优先删除重复否决/转换、恢复限定上下文、复用现有检索/综合/决策实现。
   固定输入回放与相关回归先证明处理改变，再冻结候选做开发复测；12题全部保留，不能只挑
   修好的题。初测及复测总上限36个候选执行，不新增开发题、不逐题例外，不构造新的研究平台。
   实现/数据准备/评审可分工，产品持久化仍单实例单worker，代码由一个集成者统一提交。
   当前可检查的具体限制包括：来源范围选择每源1200字符、综合最多5个source view和8个问题行。
   这些是已读到的机制，不是已证实的本轮内容根因；只有开发材料显示它们丢失了决定性依据才
   合并/调整，仍保留总预算、限定语义和安全边界。不得只增加正文长度或模型调用就宣称改善。
3. **12题未见校准**：开发候选达到第6.7节准入要求后，完成最终工程全套和独立复核，冻结代码。
   校准候选/基线各一次，独立盲评；候选至少11/12有据可用、12/12完成、关键错误0，并满足
   证据支持、测量身份和评审门槛。撤回先前“仅1题通过即可进正式”的建议。校准不通过即停
   正式准入；该题集一旦用于改产品即转开发，不能原题复测后称为未见达标。
4. **120题正式批次**：校准与总资源线均满足时连续执行；普通内容失败计入，不逐例请示。
   正式期间不得改产品、模型、数据、rubric或择优补跑；已封存正式集不作为调参反馈。
5. **全量评审与交付**：完成所有取得报告的第一评审及冻结复核；按协议复算 N/S/R/E、支持率、
   关键错误、效率、配对差异及区间；完成实际使用走查和最小展示包。基线更好也照报，不要求
   多节点必须赢；但真实质量未达到冻结门槛时不得宣布产品达标或临时降低门槛。

建议验收标准仅在[评估协议第6.7节](product-effectiveness-optimization.md#67-最后一轮验收建议待批准2026-10-23)
维护。上述合并开发/校准、取消重复、调整复核范围均是本次**待采纳建议**，不自行覆盖现行协议。
第10轮不是无限工作容器：范围内可连续完成步骤，新增产品路线/额外运行须另决，不拆成第11轮。

### 7.5 时间、费用与批准对象

用户允许提高资源投入但要求尽快；本次不把第9轮的80–140小时估计作为已核实必要耗时，也不
承诺几小时能完成。删除48次运行只能减少相应执行/评审，不能消除144题作者与240份正式报告
内容评审的劳动。以实际记录拆开计算：

- 总执行工作窗口 = 必要实现/验证 + 数据准备/参考核验 + 运行与运维 + 内容评审/交付；等待用户
  的时间单列。运行和评审若重叠，分别报工作量和实际日历时长，不简单相加当工时。
- 一次完整第一评审平均 m 分钟，300份上限对应 `300×m/60` 小时，尚未含第二评审；m需实测
  实测，不能以读取几段文字冒充完整断言审查。数据可共用参考核验，但case标准仍须逐例准备。
- 若两臂各沿用900秒执行上限，300次分臂执行的宽松串行算术上界是75小时，不是预计耗时；
  共享采集不重复记账，排队/人机等待、准备和评审另外记录。
- 单例候选保留 durable 60,000 token/96 LLM/72 retrieval/900,000 active ms 上限；基线的
  `shared + baseline` 同样不得超过对应预算。两臂60,000上限的300次宽松token总界为
  18,000,000（共享只计一次后更小），不是实际用量或现金报价；缺失用量保守占账，不以
  “已知token尚少”继续放行。HTTP/页面/核验额度须在实际派发点有守卫，不能沿用文档数字当实现。
- 校准后根据当前维护版本的实际token、请求、耗时以及评审速度更新正式批次预测；旧实验
  单例不作本候选的计费/耗时承诺。价格未知仍可采用明确的资源额度，但须用户明确接受费用
  unknown；不能把未定金额理解为任意付费。

后续需要批准的对象是：本节有限实施范围、第6.7节验收提案、分阶段数值额度/停止线；可以用
一次有条件整批授权覆盖校准和正式阶段，无需每题确认。数值额度须先与实际实现可强制执行的
上限一致。本次审查未派发研究，dsh收到用户转发的执行指令后才开始该批次。

### 7.6 质量优先委托的执行边界（用户转发指令后生效）

- 交付目标是达到第6.7节冻结标准的产品与真实指标，不能以“批次已跑完”结案为成功。
  未执行前不许承诺未知分数；资源增加不能消除模型失误、站点变化、抽样和评审误差。
- 开发数据可以用于修改；未见校准和正式数据不得泄漏给实施者。开发两批改进用尽仍不达准入，
  或未见校准失败时，停下大额正式派发，报告缺哪项能力、最短替代路线与剩余工作量；不把它
  改称目标已达成，不隐瞒增加第三批修改/新校准集。这个边界不能通过更名“内部步骤”规避。
- 研究/校准/正式总分臂执行≤300；实际LLM请求≤20,000；Tavily POST≤10,000；
  token保守计账总额≤18,000,000。保留durable单run现有上限；基线shared+arm同口径限额，
  单次逻辑综合最多3次现有传输尝试。不是要求花满，也不是新算法轮次额度。
- 参考核验最多864个URL条目（144×6，重复URL/版本/hash复用核验）；参考、研究采集、引用核验
  的安全页面抓取合计≤10,000次逻辑尝试、≤40,000次实际HTTP（含redirect）。每页大小、类型、
  编码、DNS/IP固定、redirect及期限保持当前安全边界。静态provider请求另记，不能把安全fetch
  计数冒称全部HTTP。额度必须在实际派发前守卫；只写authorized字段不构成可执行预算。
- 默认保留当前DeepSeek Flash产品模型。若开发证据证明来源/可见上下文已充分而模型仍不足，
  应提交一次整体模型配置替换方案，包含可用性、凭据需求、两臂公平性和预算；不再以题目规则
  代替模型能力。当前委托不凭空假定新provider已配置，不恢复退役变量/隐式凭据fallback。
- 第三方模型裁判和付费benchmark保持0。允许隔离的助手角色并行准备、核验和评审；其运行
  用量按平台能取得的数据单列，未知为unknown，不宣称助手评审免费或等于专家评审。需要新增
  provider、人工服务采购或外部消息时，集中说明缺失条件，不擅自采购或联系。
- 排程目标24–48小时，不是完成承诺或新硬截止。第一工作段约6小时内给出实测速度、当前质量、
  主要损失和剩余时间预测；预计超过48小时立即说明具体瓶颈。不得到最后才披露长期工程量，
  也不把等待用户时间累加为主动工时。代码/生产运行保持串行集成；独立资料与评审可并行。
- 原报告/历史分母/学习文件用户修改保留；未获另外授权不push、改历史、合并实验树或改外部简历。

### 7.7 内容评审的实际工作

内容评审是逐份核对“报告是否回答原需求，关键判断是否被适用来源支持”。它不改原报告，也不
重做完整研究；新核验资料可以揭示错误，却不能事后补进原报告冒充原有证据。

每份使用原请求/必答项/硬约束、未手修报告、当次保存来源、预冻结参考与rubric。先标出问题
答案位置，再普查决定性事实（含未引用、否定、量化和条件前提），记录报告定位、来源段落、
版本/场景、full/partial/none/unknown与错误严重性。最后判定有用选择/条件分支/恰当暂缓、
一致性与安全。普通背景、排版重复不是新的决定性断言，不强求每一句都引用。

“全部”是所有取得的原报告都接受上述第一评审：正式最多240份，加校准24份、开发最多36份。
无报告的运行失败仍进入S，由程序记录失败而非伪造一份内容评分。第二评审按冻结抽样与风险
规则执行，不能把只评通过子集当全量；也不要求用户亲自读完300份。

自动化负责hash/身份/URL对应、计数和聚合；独立评审者负责适用性、推论和取舍的语义判断。
助手可协助定位/核验，不能用多模型同意充当客观真值。只有助手评审就明确按助手口径发布；
如要声称专家校准，必须实际安排有领域判断能力的人独立核对校准/分层抽样，不能凭预算假设
该人员已经到位。方法参考：[Anthropic研究Agent评估](https://www.anthropic.com/research/demystifying-evals-for-ai-agents)。
