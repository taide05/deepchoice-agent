### 7.3 最小实施契约

**A. 配对适配，不另建研究算法。** 在真实 source evaluation 完成后、冲突检测前留存有界共享
证据与失败状态，内容/身份 hash 在两臂实际输入处核对。仅保存消费者所需的允许字段；不读取
LangGraph 私有数据库，不把 RunContext、租约、秘密或完整私有状态写入公共结果。候选继续走
当前产品链路；基线用相同 manifest 模型/参数、相同有界窗口和当前综合实现，无冲突、自审或
失败后语义重写。共同引用绑定、安全边界和渲染复用；可能产生外呼的验证同样预算化并分臂记账。
不通过 `run_manifest=None` 激活旧提示/纠错分支，也不伪造运行租约来获得预算。

现有 LLM helper 为一次逻辑生成最多3次传输尝试（2次重试，SDK重试0）。应明确继承相同传输
失败策略；“一次综合”不等于只记一次实际请求。共享来源评分本身可能调用模型，归 shared；
候选的冲突/自审为增量。若发现实际路径还会改写/扩充来源，先处理公平性，不用不同输入继续跑。
基线必须有实际生效的派发前资源守卫；裸调 helper 不是实现。此适配是待完成工作，尚未验证成功。

**B. 收拢现有批量工具。** 在 `final_batch.py` 及既有 collector 上补校准 split、配对身份、
授权清单与实际资源上限、resume 对账、报告 hash 与多评审绑定、协议指标汇总。来源/执行
失败可计量，预算/身份/未知提交失败必须停止新准入。不得只修改 JSON 中的 `authorized`、
`eval_ready` 就越过实际核验；未结算提交先用产品状态对账，不删日志后重发。无报告失败保留
在 S，不能因基线未执行而从共同计划 N 消失；各臂与完整配对子集分别列分母。

**C. 数据与评审。** 保留分层，删除“唯一候选对即独立需求”的假设；每题明确真正影响选择的
少量必答项，不扩成完整部署审计。参考允许条件答案和证据不足，不强填唯一 winner。来源的
官方性、版本、日期和适用范围逐项判定，未见资格由独立准备/历史查重确认；看过结果的题
不可挪回正式集。代码锁定前实现者只见类别/契约，参考不进入研究/检索缓存/学习文件。
复核者类型诚实标注；助手独立复核仍是助手评审，不宣称人工/专家校准或0计算成本。

### 7.4 最后一轮的执行顺序与停止点

1. **有限准备**：先关闭 A/B 中的测量阻断，完成针对性测试、最终全套和必要独立复核；代码
   冻结。独立准备者完成132个有效需求及参考；按已批准范围执行核验，研究输入与评审参考隔离。
2. **12题校准**：获得明确额度后一次执行，盲评并校准评审操作。不得逐题修代码、换题或补跑。
   校准必须证明配对/预算/原产物身份可核对、评审分歧可处理，并至少取得一份按协议第2节
   真正通过的候选原报告；不要求12题全通过。若全无合格报告或测量方法失效，停止付费准入并
   给出具体原因和已完成交付，不能靠“还剩一轮”强行跑120题，也不自动开启下一补丁轮。
3. **120题正式批次**：校准准入与总资源线均满足时，依预先批准的条件连续执行；普通内容失败
   保留并计入，不逐例请示。正式前冻结评审规则和全部身份；校准用于修产品的情况下，不得将
   原冻结候选/校准合格继续沿用，本方案不预支这种额外修复/重跑。
4. **全量评审与交付**：完成所有取得报告的第一评审及冻结复核；按协议复算 N/S/R/E、支持率、
   关键错误、效率、配对差异及区间；完成实际使用走查和最小展示包。基线更好也照报，不要求
   多节点必须赢；但真实质量未达到冻结门槛时不得宣布产品达标或临时降低门槛。

建议验收标准仅在[评估协议第6.7节](product-effectiveness-optimization.md#67-最后一轮验收建议待批准2026-10-23)
维护。上述合并开发/校准、取消重复、调整复核范围均是本次**待采纳建议**，不自行覆盖现行协议。
第10轮不是无限工作容器：范围内可连续完成步骤，新增产品路线/额外运行须另决，不拆成第11轮。

### 7.5 时间、费用与批准对象

用户目前无法确定时间和费用上限；本次不把第9轮的80–140小时估计作为已核实必要耗时，也不
承诺几小时能完成。删除48次运行只能减少相应执行/评审，不能消除132题作者与240份正式报告
内容评审的劳动。以实际记录拆开计算：

- 总执行工作窗口 = 必要实现/验证 + 数据准备/参考核验 + 运行与运维 + 内容评审/交付；等待用户
  的时间单列。运行和评审若重叠，分别报工作量和实际日历时长，不简单相加当工时。
- 一次完整第一评审平均 m 分钟，264份上限对应 `264×m/60` 小时，尚未含第二评审；m需校准
  实测，不能以读取几段文字冒充完整断言审查。数据可共用参考核验，但case标准仍须逐例准备。
- 若两臂各沿用900秒执行上限，264次分臂执行的宽松串行算术上界是66小时，不是预计耗时；
  共享采集不重复记账，排队/人机等待、准备和评审另外记录。
- 单例候选保留 durable 60,000 token/96 LLM/72 retrieval/900,000 active ms 上限；基线的
  `shared + baseline` 同样不得超过对应预算。两臂60,000上限的264次宽松token总界为
  15,840,000（共享只计一次后更小），不是实际用量或现金报价；缺失用量保守占账，不以
  “已知token尚少”继续放行。HTTP/页面/核验额度须在实际派发点有守卫，不能沿用文档数字当实现。
- 校准后根据当前维护版本的实际token、请求、耗时以及评审速度更新正式批次预测；旧实验
  单例不作本候选的计费/耗时承诺。价格未知仍可采用明确的资源额度，但须用户明确接受费用
  unknown；不能把未定金额理解为任意付费。

后续需要批准的对象是：本节有限实施范围、第6.7节验收提案、分阶段数值额度/停止线；可以用
一次有条件整批授权覆盖校准和正式阶段，无需每题确认。数值额度须先与实际实现可强制执行的
上限一致。本次审查不是该授权，dsh仍保持停止。
