## 2. 评审规则与资格

本轮沿用 key-claim-occurrence-v1：

- rubric 0/1/2 分别表示错误或遗漏、部分正确但缺条件、正确且说明条件；
- 关键声明包括直接支撑推荐/否决、关键数字、风险边界和适用性推论；同一声明在报告不同位置
  重复出现时按 occurrence 分开；
- support 使用 supported / partial / unsupported / unknown / uncited；
- quality 使用 eligible / ineligible / unknown；只有适用的一手原始依据可记 eligible；
- 台账对纳入的关键语义声明逐处完整原子化；普通背景、纯元数据及不承担技术判断的标题按契约
  排除，不进入分母。

严重性在任何 S1 修改和新测量前冻结：

| 级别 | 判定 |
|---|---|
| 重大（major） | 已确认错误或遗漏的安全、可靠性、数据完整性、硬性约束足以反转/实质改变决策，或命中冻结案例的 major-errors；不能由均分抵消 |
| 高 | 决策关键条件、适用证据或校准缺失，可能使用户采取错误行动，但现有材料不足以确认 major |
| 中 | 降低解释、可执行性或效率，单独通常不会反转选择 |
| 低 | 表达或精度问题，不改变决策和安全边界 |

## 5. 首要根因与代码证据

首个可验证假设是：**当前结论 schema/提示过度强制 Winner 与排名，而关键约束、证据不足和
引用 unknown/unsupported 没有成为决策强度门控。**

静态证据：

- conclusion_synthesizer.py 的 prompt 组装只传 task["query"] 与 scene_context，没有显式传入
  task.constraints 或 sub_questions；第 48–49 行又要求按固定顺序选出具体技术 Winner。
- 同文件的 constraint-fit validator 会把大多数 context_dependent 改成排名首位，只在所有候选
  fit 都为 low 时允许保留。
- what_why_how.py 已能渲染 context_dependent，所以当前限制主要不是模板缺能力。
- evidence_decision_gate.py 只实现已批准的 evidence-insufficient 单 gate；limited-report 路径
  复制已有 final_recommendation，因此 P07 可以同时出现受限说明、Winner: uv 与“不能排名”。
- 引用验证发生在合成之后，适合标记问题，不会自动收回决定性结论。

P07 的零证据 Winner 和 P08 的“缺口齐全但 100% Redis”是最直接反例；P04 说明同一根因也会遗漏
可靠性硬条件。该假设不包含 P08 supplemental-context 恢复失败，也不授权新增 HITL 类型。

## 6. S1 执行卡：constraint-aware conclusion v1

### 单一主要变量

让合成与受限报告执行同一个“约束感知、证据校准”的结论契约：

1. 将冻结请求的 constraints 与 sub-questions 显式输入合成，并要求逐项标记 satisfied /
   contradicted / unknown；
2. 重大未知或决定性声明没有适用证据时，允许 context_dependent/“暂无唯一胜者”，不得靠
   lexicographic 或来源数量强制 Winner；
3. limited report 必须清除具体 Winner/排名，只保留条件分支、验证计划和回退；
4. 当冻结约束涉及可靠性/迁移时，强制逐项回答相应责任、验证指标、触发与回退；证据未覆盖
   投递语义或幂等时必须明确 unknown，不能用通用架构描述替代；
5. 不改变检索来源、预算、模型、单 HITL 种类、公共生命周期或引用状态枚举。

预计实现边界是 conclusion synthesizer 的 prompt/validator、limited-report 后处理、相应 renderer
和离线测试；如自审只需要消费新字段，可做同一契约内的最小修改。不得同时优化 conflict detector，
否则无法解释局部配对结果。

### 离线验收

- P04 fixture：不得把 broker/result backend 写成自动可靠或 exactly-once；必须把至少一次/重复
  执行可能性和任务幂等责任标成已证实或 unknown，并给出阶段性迁移/恢复验证。
- P08 fixture：约束未知时不得输出具体 Winner、#1 排名或“100%”；必须列决策分支和所需信息。
- P07 limited fixture：受限报告不得保留具体 Winner/排名，试点、指标与 Poetry 回退仍在。
- P01 regression：保留 SQLite 的条件性推荐、单 writer 边界、备份/迁移触发，不退化成无结论。
- 所有决定性句子若无适用证据，必须在句旁标记 unknown/condition 或省略；不得借其他引用编号。
- 相关测试、完整 suite、smoke、静态检查和独立只读复审通过后，才有 live 资格。

### 局部 live 方案（规划，不是执行授权）

协议 ID 拟为 product-optimization-s1-constraint-aware-v1，必须在运行前单独落成机器可读冻结文件。
目标案例 **P04、P08**，回归案例 **P01**；P07 先作为 deterministic limited-report 离线回归。

- 若产品 prompt/代码身份改变，最多 1 个新 P01 资格；
- 三例 × baseline/candidate 两版 × 2 重复 = 12 个 run；连同资格上界 13；
- baseline 与 candidate 使用同一不超过 7 天窗口、同模型/依赖/知识/预算，顺序随机、标签盲化；
- 两个 target 的 candidate 两次都须优于配对 baseline，P04/P08 均无 major 且无 0；P01 不新增
  major，决策/引用/完成率不降；
- 只证明三例的局部效果，不外推开发集或保留集；Trace 在内容锁分之后读取。

按当前账本，若执行满 13 则为 103/134，仍为 S3 的 24 个新 run 保留空间并余 7；这只是算术，
不能从余额推导立即运行权限。

### 停止与分流

- 离线反例不通过：不启动 live，继续最小修复；
- 新候选资格失败、身份/安全/预算/租约异常：停止新准入，完成已准入收尾和离线归因；
- 两次连续付费停止仍没有有效配对：触发目标复议，不追加同类采样；
- target 无一致改善或 regression 退化：关闭该假设，不换案例刷分，下一候选方向为来源适用性/
  benchmark 身份；
- 普通 citation 5xx 是否仅记 unknown/warning 仍是未实施提案，本 S1 不修改现行停止规则。

S1 局部通过后回到 [当前地图](current-roadmap.md) 重查 Q1–Q5/E1/R1/M1；不能因为一个方向完成就
宣布产品通过。S3 保留集仍需未暴露 reviewer 的盲评和人类锚点校准，C1 仍需单独处理。

## 7. S1 离线实现与证据边界

本轮执行范围为约束感知结论的实现、离线验证、复审及本地提交，研究账本保持 90/134。
S0 逐例评分、360 条台账及其原始绑定不回填为新候选结果。

- 合成显式保留冻结请求与分析生成的约束/子问题；图状态补充可选 constraints。
  稳定 ID 逐项补齐回答，缺项、无可用来源绑定或关键未知时撤回确定胜者/排序。
- 新 requirement_assessments、decision_branches、action_plan 将未知、条件、验证、
  触发和回退提供给三种模板与自审；可靠性/迁移相关请求增加通用操作责任检查。
- 决定性引用检查仍是有界的词法/可达性检查。未通过时只标记未知并降低结论强度，
  不推断事实为假；已通过也不声称语义或来源适用性得到证明。
- 用户受限报告和预算受限报告清除原确定胜者、排名及确定性总结，保留条件和待验证计划。
  所有逐项判断改为 unknown 并清除引用绑定，预算在引用验证前停止也不得保留“已证实”结论。
  单一 HITL 门仍要求结构证据不足与方向不确定，恢复、预算与安全边界保持原契约。
- 新 synthesis v4 及三种模板版本使旧 run 同 run 恢复安全拒绝；旧结果保持可读。
  冻结 smoke-v1 的 12-case 数据及预期不变，资产版本和有意变化的渲染输出更新 baseline。
