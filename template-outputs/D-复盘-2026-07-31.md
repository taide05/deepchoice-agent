# DeepChoice 模板 D：项目复盘

> 执行时间：2026-07-31 | 基准 commit：`455e805`

## 1. 设计决策审计（5条）

### 决策 #1：9 Agent DAG 管线 vs 单 Agent 巨型 Prompt

- **决策**：将技术选型研究拆成 9 个独立 Agent 节点的 DAG 管线，而非一个大 Prompt 一次调用
- **当时理由**：技术选型是多阶段认知任务（拆解→搜索→评分→仲裁→综合→审查），每个阶段需要不同的推理逻辑和工具调用。单个巨型 Prompt 的 LLM 注意力分散、难以增量修正
- **代码证据**：`orchestrator.py:60-93` — `_create_workflow()` 方法创建 9 节点 StateGraph，`_route_after_review()` 实现条件路由
- **替代方案 B**：单 Agent + ReAct 循环（自主规划→执行→反思），AutoGen/CrewAI 对话式编排
- **重来判定**：仍选 A。DAG 模式对步骤明确的研究管线有天然匹配度——每个节点的输入输出契约清晰，质量门禁可精确插入。对话式 Agent 对这类确定性问题会引入不必要的协商开销
- **可测试断言**：9 Agent DAG 管线的最终推荐准确率应优于单 Agent ReAct（同 LLM 条件下）。如 B 方案更好，应看到 Top-1 Accuracy 显著提升（>10pp）
- **面试价值**：9/10。这是"为什么不是简单方案"的经典追问

### 决策 #2：信源评分用规则引擎而非 LLM

- **决策**：SourceEvaluator 的四维评分（Authority/Timeliness/Consistency/Verifiability）全部用规则计算，不调 LLM
- **当时理由**：评分需要确定性、可复现、低成本。同一来源今天 8 分明天 6 分不可接受。28 条来源全用 LLM 评分是 28 次 API 调用，用规则引擎是 0 次
- **代码证据**：`source_evaluator.py` — `classify_source_type()` URL 模式匹配、`score_timeliness()` 日期差值计算、`compute_consistency()` 两轮同类项聚合，全部纯函数
- **替代方案 B**：LLM-as-Judge 逐条评分（如用 GPT-4 给每条来源 1-5 分）
- **重来判定**：仍选 A。规则引擎的确定性在 benchmark 复现时是关键优势。但承认规则粗糙——分类函数只检查 URL 和 snippet 关键词，medium.com 上的深度技术文章和 CSDN 水文同分
- **可测试断言**：将 SourceEvaluator 替换为 LLM-as-Judge 评分（至少 3 个不同 case），预期 Top-1 Accuracy 波动 > 5pp（规则 vs LLM 排序差异大），但 Latency P50 增加 > 30s
- **面试价值**：8/10。展示"知道什么时候不用 AI"

### 决策 #3：两阶段冲突仲裁（flash 批量 + pro 单点）

- **决策**：冲突检测先让 flash 批量裁决所有矛盾对，再挑出最模糊的一对（分数差最小）用 pro 重裁
- **当时理由**：全用 pro 仲裁 P95 延迟 410s，改为 flash 初裁后用确定性规则（分数差 >= 2.5）处理大部分，只为最需要推理能力的 1 个 case 走 pro
- **代码证据**：`conflict_detector.py` — `_arbitrate_batch()` flash 批量仲裁 → `_select_hardest_case()` 按分数差排序挑最小 → `_arbitrate_with_evidence()` pro 重裁 + 6 路工具内联证据收集
- **替代方案 B**：全部用 pro 仲裁（质量上限高，但成本/延迟不可控）；全部用 flash 仲裁（快但最复杂 case 可能误判）
- **重来判定**：仍选 A。这是"好、快、便宜"三选二经典 trade-off 的工程化解决。P95 从 410s→164s（-60%）验证了这个设计的价值
- **可测试断言**：关闭 pro fallback（仅 flash）跑 50 case，预期 Top-1 Accuracy 下降 < 2pp（大部分矛盾对分差明显），但模糊 case（TC-0031 PostgreSQL vs MySQL 金融场景）的预测可能翻转
- **面试价值**：10/10。最出彩的工程决策——分级降级、资源聚焦、量化验证

### 决策 #4：否定词 + LLM 扫描两级冲突发现

- **决策**：先 BGE-M3 嵌入计算标题余弦相似度（>= 0.6）+ 否定词检测做粗筛，再用 LLM CONTRADICTION_SCAN_PROMPT 并发扫描候选对做精判
- **当时理由**：纯否定词匹配产生 100% 假阳性（标题里有 "not" 不一定是矛盾），纯 LLM 扫描 50 case 的 N(N-1)/2 对 token 成本爆炸。两级管道：否定词粗筛 O(n²) → LLM 精判只扫候选对
- **代码证据**：`conflict_detector.py` — `_compute_similarity_matrix()` 批量 BGE-M3 + `_detect_by_negation()` 否定词检测 → `CONTRADICTION_SCAN_PROMPT` LLM 并发扫描。最新 commit `455e805` 将否定词匹配替换为 LLM 语义扫描
- **替代方案 B**：纯 LLM 逐对扫描所有来源对（质量上限最高，但成本 O(n²) × API 调用）
- **重来判定**：仍选 A。但承认 0.6 阈值是经验值（实验调参），否定词集合（30+）是启发式的。已知漏判场景：两篇都用肯定措辞但数据相反的 case
- **可测试断言**：用 10 个含已知相反结论但无否定词的 case 测试，预期当前方案的检测率 < 30%（标题措辞不含否定词时漏判）
- **面试价值**：7/10。展示"管线优化的演进思路"（否定词→LLM 扫描→未来？数值提取）

### 决策 #5：quality_signals 分布式质量感知

- **决策**：每个 Agent 输出时附带自己的 quality_signals 元数据，SelfReviewer 汇总上游信号而非从零扫描 state 做审查
- **当时理由**：效率——SelfReviewer 重新扫描 28 条评分+若干矛盾对再做判断既不经济也不准确。借鉴微服务可观测性中的分布式 tracing 思路
- **代码证据**：每个 Agent 的 `run()` 方法返回 `quality_signals` dict → `orchestrator.py` StateGraph 累积到 `state["quality_signals"]` 列表 → `self_reviewer.py` 汇总
- **替代方案 B**：SelfReviewer 从 state 中自己重新计算所有质量指标（集中式）
- **重来判定**：仍选 A，但承认当前实现有缺陷——quality_signals 是 list-of-dict 的松散约定，没有 Pydantic 模型约束。Tool Evolution Engine 项目中做了改进（QualityRegistry Pydantic model）
- **可测试断言**：如果 SourceEvaluator 误报 quality_signal（如宣称 high_score_count=12 实为 8），SelfReviewer 不会交叉验证，confidence 评定受影响。用注入错误 quality_signal 的集成测试验证
- **面试价值**：8/10。展示"从自己项目中发现不足并在下一个项目改进"的成长叙事

## 3. 踩坑记录（3条）

### 坑 #1：否定词匹配 100% 假阳性 —— 从规则到 LLM 的演进

- **现象**：BGE-M3 相似度 >= 0.6 + 标题含否定词 → 判为矛盾对。50 case benchmark 跑下来，检出 23.9% 的矛盾对全是假阳性——标题写 "Why X is not the best choice" 的文章和 "X is a good choice" 被判定为矛盾，实际两篇结论一致
- **根因**：否定词是表面信号而非语义信号。"not" 在标题中可能是修辞（"Why not X"）、否定前提到肯定结论、或否定一个不相关的主张。规则匹配不理解语义
- **修复**：`455e805` — 将否定词匹配替换为 LLM CONTRADICTION_SCAN_PROMPT 语义扫描。flash 模型并发扫描候选对，判断两篇文章是否确实在同一个维度上持相反结论。假阳性从 100% 降为 0%
- **如果一开始就知道**：直接用 LLM 做语义判断，不浪费一轮迭代在否定词上。但否定词作为粗筛的"触发条件"仍有价值——用来决定哪些候选对值得 LLM 扫描，降低 token 成本
- **可测试断言**：构造 10 对标题含 "not" 但结论一致的 case + 10 对不含否定词但结论相反的 case。LLM 扫描应正确区分前 10 对（判非矛盾）但漏判后 10 对（标题无否定信号）

### 坑 #2：否定词检测仅看标题，漏掉 snippet 矛盾信号

- **现象**：`362ab49` 之前，否定词检测只检查文章标题。一篇标题为 "FastAPI performance analysis"（中性、无否定词）但 snippet 里写 "FastAPI significantly underperforms Flask in real-world tests" 的文章不会被识别为矛盾
- **根因**：设计假设"矛盾一定在标题中体现"，实际社区/博客文章的标题常是中性或正面的（SEO 友好），矛盾在正文
- **修复**：`362ab49` — source_evaluator 传递 snippet 字段到 conflict_detector，否定词检测扩展为 title+snippet 联合扫描
- **如果一开始就知道**：设计 conflict_detector 的输入 schema 时就包含 snippet，但当时的架构里 source_evaluator 不传 snippet（只传评分后的 url+title+score+date）
- **可测试断言**：用 5 个标题中性但 snippet 含明显矛盾信号的 case 跑 conflict detection，预期检出率显著高于仅标题版本。具体数值需跑对比实验

### 坑 #3：conclusion_synthesizer flash 输出格式不稳定

- **现象**：`6631bbc` 之前，conclusion_synthesizer 用 flash 模型，输出有时不包含显式 Winner 名称——报告里写了长篇分析但没有 "推荐: X" 的明确结论。benchmark 的 Top-1 Accuracy 被 report 解析失败拖低
- **根因**：flash 模型在遵循结构化输出指令方面弱于 pro 模型。prompt 里有 "必须输出 Winner: X" 的指令，但 flash 有时跳过、有时嵌入在段落中间
- **修复**：`6631bbc` — conclusion_synthesizer 从 flash 升级为 pro。pro 模型遵循指令更稳定，Winner 输出格式 100% 符合预期
- **如果一开始就知道**：对需要严格格式输出的 Agent 直接用更强模型，不省钱。但 flash→pro 的升级让该 Agent 的 API 调用成本增加约 3-5x——对于"综合结论"这个关键环节是值得的
- **可测试断言**：用同一批 10 个 case 跑 conclusion_synthesizer flash vs pro，对比：①Winner 格式合规率 ②Top-1 Accuracy 差异。预期 pro 格式合规率 100%，flash < 80%

## 5. 薄弱点自诊断

### 面试最怕被追问的 3 个问题

1. **"56.8% Top-1 Accuracy，对比随机猜测 50%，你觉得这个系统有用吗？"**
   - 模糊地带：技术选型本来就没有唯一正确答案，56.8% vs 50% 的差距是否足够证明系统价值
   - 应对：诚实说这是辅助决策不是自动决策，56.8% 在有据可查的前提下有意义，但承认需要更多数据点（更大 benchmark、真实用户采纳率）

2. **"信源召回率 30.4% 为什么这么低？怎么改进？"**
   - 模糊地带：138 个必须匹配的 URL 模式只命中 42 个——主要是 Tavily API 不会返回官方文档域名（redis.io、kubernetes.io 等）
   - 应对：这是检索源覆盖问题而非算法问题。改进方向：增加 Official retriever 的直连能力（直接爬官方文档站而非依赖搜索引擎）

3. **"9 Agent 串行管线，如果第 3 个 Agent 挂了怎么办？"**
   - 模糊地带：当前只有检索器级别容错（return_exceptions=True），Agent 级别没有 fallback 或降级策略
   - 应对：这是已知设计限制。生产环境需要 Agent 级别的 retry + circuit breaker + 降级输出（缺少 Review 时跳过不阻塞）

### 如果给两周时间，优先级最高的 5 个改进

| 优先级 | 改进 | 量化目标 | 理由 | 涉及文件 |
|:--:|------|---------|------|---------|
| 1 | 官方文档直连检索 | 信源召回率 30%→60% | 当前 30% 太低，面试硬伤。直接爬官方 docs 站（FastAPI docs、PostgreSQL docs）而不是依赖搜索引擎间接发现 | `retrievers/official_docs.py`（新增直连）+ `annotated_cases.json`（更新 must_find_sources） |
| 2 | Agent 级别容错 + 降级 | 成功率保持 100% 前提下，单 Agent 故障恢复率 90% | 当前如果 conflict_detector 或 conclusion_synthesizer 的 LLM 调用失败，整个管线中断后用 retry 重跑 | `orchestrator.py`（circuit breaker）+ 各 Agent `run()`（try-except 降级输出） |
| 3 | benchmark 扩大到 200 case | 统计显著性 p < 0.05 for Top-1 > 50% | 50 case 的置信区间太宽。200 case 能区分 53% 和 62% | `annotated_cases.json` + `run_baseline.py` |
| 4 | 冲突检测加数值提取 | 检测率 23.9%→50%+ | 当前依赖标题否定词+LLM语义扫描，漏判"数据相反但措辞都正面"的场景。加 benchmark 数字提取（从 snippet 中提取性能数字并比较） | `conflict_detector.py` |
| 5 | 结果缓存层 | P50 延迟 130s→80s（同 query 命中时 < 5s） | 用户可能反复搜同类问题，Redis 缓存已跑过的研究结果 | `server/app.py`（缓存中间件）+ `redis` 依赖 |

### 每薄弱点可测试断言

- **薄弱#1**：构造 20 个含官方文档 must_find 的 case，对比当前 Tavily-only 和加入官方直连后的召回率。预期当前版本 < 35%，直连版本 > 55%
- **薄弱#2**：注入 Agent 故障（mock LLM 抛异常），验证管线是否有优雅降级而非崩溃。当前预期：崩溃
- **薄弱#3**：用 bootstrap 重抽样算 50 case 的 95% CI。预期 CI 宽度 > ±10pp，不足以区分细微改进
- **薄弱#4**：用 10 个"数据相反但标题中性"case 跑 conflict detection。预期当前检测率 < 20%
- **薄弱#5**：连续 3 次相同 query 跑管线，记录每次延迟。预期三次延迟相近（无缓存加速）
