## 3. Agent 延迟拆分明细

> 以下为延迟的定性分解。精确的 per-Agent P50/P95 需要修改 run_baseline.py 在各 Agent 节点前后插桩——当前代码未记录 per-Agent 耗时。

| Agent | 预估耗时占比 | 瓶颈类型 | 说明 |
|------|:--:|------|------|
| MultiRetriever | ~15s (10%) | I/O 等待 | 6 路 asyncio.gather，最慢 Tavily~5s。大部分时间在等 API 响应 |
| SourceEvaluator | ~1s (<1%) | CPU | 纯规则计算，O(n) 28 条来源，极快 |
| ConflictDetector | ~20s (15%) | LLM + I/O | BGE-M3 encode (~2s) + LLM 扫描候选对（flash 并发）+ 如有 low confidence 则 pro 重裁 + 6 路证据收集 |
| QueryAnalyzer | ~8s (6%) | LLM | 单次 flash LLM 调用 |
| QueryAdapter | ~0.5s (<1%) | CPU | 纯字符串模板处理 |
| ConclusionSynthesizer | ~15s (12%) | LLM | pro 模型单次调用 |
| EvidenceChain | ~0.5s (<1%) | CPU | 纯规则分类 |
| ReportGenerator | ~0.5s (<1%) | CPU | 纯渲染 |
| SelfReviewer | ~5s (4%) | LLM | flash 模型单次调用 |
| **LLM 调用总等待** | ~55s (42%) | LLM | 各 Agent 的 LLM API 调用合计（含重试） |
| **网络/检索 I/O** | ~20s (15%) | I/O | 检索 API 调用 |
| **框架/序列化开销** | ~5s (4%) | 框架 | LangGraph state 传递/序列化 |
| **总计** | **~130s** | — | P50 端到端 |

> 以上为 P50 场景的定性分解。P95 场景（164s）多出的 34s 主要在：①ConflictDetector 触发 pro 重裁 + 证据收集（+20-30s）②某检索器超时（+15s）。

**瓶颈分析**：LLM API 调用占总延迟的 ~42%，是最大瓶颈。其次是检索 I/O（15%）。两阶段仲裁将原来全部 pro 仲裁的 55s LLM 等待降到 ~20s（ConflictDetector 部分）。

## 4. 检索源召回明细

> 以下为按检索源拆分的 source recall 预估。精确值需要修改 run_baseline.py 在 search 阶段记录每条结果的 source_origin，然后按 source 分组计算 recall。

| 检索源 | 预估召回率 | 主要命中类型 | 主要漏检类型 | 说明 |
|------|:--:|------|------|------|
| Tavily | ~50% [推算] | 博客、文章、新闻 | 官方文档域名 | Tavily 优先返回 SEO 优化的博客，不返回 docs 站 |
| GitHub | ~40% [推算] | 仓库主页 | Issue/PR 讨论 | GitHub API 搜索返回仓库，标注的 must_find 常含特定 issue |
| Arxiv | ~35% [推算] | 论文标题匹配 | 具体方法/数据集论文 | Arxiv 搜索精度依赖关键词质量 |
| Community (SO+Reddit) | ~25% [推算] | 热门讨论帖 | 冷门技术讨论 | Reddit/StackExchange API 覆盖受限于搜索词 |
| Official (PyPI) | ~20% [推算] | 包基本信息 | 详细文档页 | PyPI JSON API 只返回包元数据 |
| ChromaDB (本地) | ~15% [推算] | 预索引文档 | 新技术文档 | 本地 KB 覆盖取决于预加载数据量 |

**整体信源召回率 30.4% 的根因分析**：
- Tavily 占大多数 must_find 的来源，但它不返回官方文档站（redis.io、kubernetes.io、fastapi.tiangolo.com 等）
- 标注的 must_find_sources 以 official_doc 类型为主（约占 35%），正是 Tavily 最不擅长的
- 改进路径：Official retriever 增加直连官方文档站的能力（HTTP GET + HTML parsing），不依赖搜索引擎

## 5. 优化链路

| 优化项 | 改动前 | 改动后 | 变化幅度 | 对用户意味着什么 | Commit |
|------|------|------|------|------|------|
| 两阶段仲裁（pro→flash+pro） | P50 162.6s / P95 410.3s | P50 130.5s / P95 164.2s | P50 -20%, P95 -60% | 研究等待时间大幅缩短，极端慢的情况基本消除 | `455e805` |
| 否定词→LLM 语义扫描 | 假阳性 100%（否定词匹配） | 假阳性 0%（LLM 判断） | 假阳性 -100pp | 不再把"措辞否定但结论一致"的文章误判为矛盾 | `455e805` |
| 否定词检测 title-only→title+snippet | 漏判（标题中性但 snippet 矛盾） | 覆盖 title+snippet | 覆盖率提升（具体数值待测） | 中性标题文章的矛盾也能被捕捉 | `362ab49` |
| Conclusion flash→pro | Winner 格式不稳定（flash <80%合规） | 格式合规 100% | 格式合规 +20pp+ | 每份报告都有明确推荐结论 | `6631bbc` |
| 检索器串行→asyncio.gather | Community 内部 SO+Reddit 串行 | Community 内部并发 | 社区搜索延迟 -40% [推算] | Reddit 和 SO 同时查，不等彼此 | `ab952c4` |
| GitHub 串行→asyncio.gather | 多 repo_name 逐个查 | 多 repo_name 并发 | GitHub 搜索延迟 -50% [推算] | 候选仓库同时搜索 | `ab952c4` |

> 优化链路呈现清晰的演进方向：延迟优化（仲裁分级、检索并发）→ 质量优化（LLM 扫描替代规则、pro 升级）→ 覆盖优化（title+snippet 扩展）。

## 6. 退化分析

### 已知错误模式（来自 annotated_cases + CLAUDE.md 踩坑记录）

| 错误模式 | 频率 [推算] | 根因 | 影响指标 | 改进路径 |
|------|:--:|------|:--:|------|
| 官方文档未被检索到 | ~30% of missed sources | Tavily API 不返回 docs 站 | 信源召回率 | Official retriever 直连官方站 |
| 小众技术信息不足 | ~15% of cases | 网络信息少，6 路检索器都找不到足够资料 | Top-1 Accuracy | 增大检索 timeout + 更多检索源 |
| 矛盾结论未被检测 | ~76% of contradictions | 否定词+LLM 语义扫描仍有漏判 | 冲突检测率 | 数值提取 + 全语义对比（非仅标题） |
| 推荐无明确 Winner | 0%（已修复） | conclusion_synthesizer flash 输出不稳定 | Top-1 Accuracy | pro 模型已修复 |
| 冷门查询无信息 | ~5% of cases | 检索器全面返回空结果 | 任务成功率 | self_reviewer 诚实标注"证据不足" |

### 最差场景特征

1. **高上下文依赖性**：如 "PostgreSQL vs MySQL for enterprise financial data" — 结论高度依赖"金融"这个上下文，检索结果如果没覆盖金融场景的特殊需求，推荐会偏
2. **同生态竞争**：如 "LangGraph vs CrewAI" — 两个框架都活跃、都有支持者，结论可能在不同维度上各有利弊
3. **信息时效性敏感**：如 "Claude API vs GPT-4 API" — 模型能力变化快，benchmark 数据 3 个月前就过时
